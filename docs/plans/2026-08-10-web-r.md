## 目标与边界

本阶段只完善两个已交付 Web 产品：`front-next` 响应式用户端和 `admin-next` 响应式运营管理平台。覆盖桌面与手机浏览器的导航、布局、状态反馈、键盘/触控可访问性和首屏性能，不新增、不删除、不修改预约、结算、资产、积分、商城、评价、售后、权限或通知业务规则。

不进入微信小程序；不恢复 SC10 stash；不新增独立技师端、总部端、分店端或复杂多岗位后台；不把冻结模块重新放入公开导航。视觉延续现有系统字体、白/浅灰表面、深玫瑰主操作色、铜色辅助强调和 8–12px 圆角，不进行无关品牌重设计。

## 基线审计结论

1. `front-next/src/router/index.ts` 同步导入全部页面，首页之外的预约、资产、商城、售后等代码进入首屏依赖图；应改为路由级懒加载并验证构建分包。
2. 两端主壳层都直接进入导航和页面内容，没有可见于键盘焦点的“跳到主要内容”入口，也没有路由切换后的标题/主内容焦点恢复。
3. `admin-next/src/components/AppShell.vue` 的移动导航按钮缺少 `aria-expanded`/`aria-controls`，抽屉不支持 Escape 关闭和路由切换关闭，打开时也未阻止背景滚动；页头仍显示阶段性文案“SC7 数据迁移与运营完善”。
4. 用户端底部导航和运营端移动抽屉虽已有断点，但缺少统一安全区、44px 触控目标、横竖屏/短视口和窄屏溢出契约。
5. 双端已有基础空态和错误信息，但加载状态表现分散；缺少共享骨架/状态区域、`aria-live` 与统一的禁用/忙碌语义。
6. 既有 CSS 已固定品牌色、焦点色与减少动态效果方向，可在原设计系统上增量修复，无需引入新字体、重型动画或新的 UI 框架。

## 实施任务

1. 先新增失败契约：
   - `scripts/test-web-r-ui-contract.ps1` 静态检查两端跳过导航、移动抽屉语义、路由焦点、懒加载、安全区、减少动态效果和禁止公开技师入口；
   - `front-next/tests/web-r-contract.test.ts` 与 `admin-next/tests/web-r-contract.test.ts` 覆盖路由、壳层和 CSS 源码契约；
   - 运行并记录预期失败。
2. 新增共享 Web 可访问性基础：跳过导航链接、稳定的 `#main-content`、路由切换后的页面标题与主区域焦点、状态区域 `aria-live`、全局可见焦点和减少动态效果兜底。
3. 完善用户端壳层：
   - 路由级懒加载所有页面，保持现有 URL、鉴权与滚动行为；
   - 桌面导航在中等宽度下安全收缩，手机底部导航适配 `env(safe-area-inset-bottom)`、横屏和短视口；
   - 主内容为底部导航预留安全空间，交互目标至少 44px，超长账号名和文案不制造横向溢出；
   - 公开用户端不新增技师入口，冻结兼容代码不删除。
4. 完善运营端壳层：
   - 移动抽屉增加展开状态、控件关联、Escape/路由切换关闭和背景滚动锁定；
   - 为移动端显示当前页面标题和明确的账号/门店范围，去除过时阶段文案；
   - 窄屏只保留已确认的高频入口，桌面完整运营导航保持不变；
   - 统一表格滚动容器、筛选栏、页头操作和对话框在 320–900px 的结构行为。
5. 新增双端共享状态组件/样式：内容骨架、空态、错误/成功状态、按钮忙碌与禁用语义；优先替换高频入口中的裸文本 loading，不改变数据请求或提交逻辑。
6. 在 `scripts/verify-web-r-ui.mjs` 建立真实浏览器矩阵，使用固定合成账号验证：
   - 用户端：首页、项目、预约、资产、商城、消息、评价售后、个人中心；
   - 运营端：运营总览、今日工作台、预约与排班、履约与售后；
   - 视口：390×844、768×1024、1440×960，并补充 844×390 横屏；
   - 检查无页面横向溢出、主导航可达、焦点可见、Escape 可关闭、44px 触控目标、页面标题、无浏览器异常和关键资源失败。
7. 增加 `scripts/verify-web-r-runtime.ps1`：显式参数化并预检端口，从两个独立干净 Compose project 连续运行后端全量测试、双前端测试与构建、容器健康、重启、SC8 核心业务回归和 WEB-R 浏览器矩阵。不得随机选择端口。
8. 更新 `README.md`、`PRODUCT.md`、`DESIGN.md` 和 `CONTRIBUTING.md` 的阶段状态；在 `docs/verification/WEB-R/` 留存起点 SHA、计划 SHA、版本、命令、RED 证据、构建分包、浏览器矩阵、两轮日志、截图索引、风险和来源限制。

## 测试优先顺序

1. 运行静态契约和双端定向测试，确认跳过导航、抽屉语义、焦点管理、路由懒加载和安全区缺失而失败。
2. 先做壳层/路由最小实现并使定向测试通过，再调整共享 CSS 和状态组件。
3. 运行双前端全部测试、类型检查与生产构建，核对用户端非首页页面形成独立 chunk。
4. 运行浏览器矩阵并保存基线/修复后截图；发现溢出、控制台异常、不可达交互或触控目标不足时回到实现修正。
5. 连续两次运行正式 WEB-R 验收；任何代码、Compose 或验收脚本修正后，两轮均从 Run 1 重新开始。

## 验收与停止条件

- 两端在 390×844、768×1024、1440×960 和手机横屏下无文档级横向溢出，主任务和关键操作无需缩放即可完成。
- 键盘用户能跳过导航；路由切换后页面标题和主区域焦点正确；移动抽屉可由按钮、Escape、遮罩和导航选择关闭，打开时背景不滚动。
- 底部导航、抽屉按钮和高频操作满足至少 44px 触控目标并适配安全区；减少动态效果偏好下无位移或连续动画。
- 用户端生产构建按路由分包；双端无新增浏览器异常、类型错误或关键请求失败。
- SC8 已验收的注册、预约、卡项、积分、商城、履约、评价和售后结果保持一致，后端业务测试全量通过。
- 两轮干净环境验收通过并完成证据、提交和 `web-r/v1.0.0` 标签后立即停止；不自动恢复或进入 SC10。
