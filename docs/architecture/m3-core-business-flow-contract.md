# M3 核心业务闭环实现契约

## 模块边界

- `appointment`：唯一拥有预约状态写入；对外提供创建、确认、到店、开始服务前状态推进和完成联动。
- `servicecare`：拥有服务记录、护理事实、顾客确认和追加式更正；不通过控制器直接拼接跨模块 SQL。
- `inventory`：拥有库存余额和流水；服务完成通过应用服务协作，使用数据库事务和乐观版本。
- `transaction`：拥有订单和支付状态；创建与支付分别校验幂等键和请求哈希。
- `outbox`：保存领域事件，和业务事实在同一数据库事务提交。
- `idempotency`：V3 命令幂等入口；同键同载荷安全重放，同键异载荷返回 409。
- `client` 与 `v3/operations`：只做认证、DTO 适配和稳定响应，不承载状态机规则。

## 状态机不变量

### 预约

```text
PENDING → CONFIRMED → CHECKED_IN → IN_SERVICE → COMPLETED
```

- 非法跳转返回 409。
- `IN_SERVICE → COMPLETED` 只能由服务完成事务驱动，普通预约状态接口不得绕过护理事实和库存联动。
- 取消、爽约必须按当前状态和原因规则执行，并保留历史。

### 服务记录

```text
DRAFT/未创建 → IN_PROGRESS → COMPLETED
                         └→ VOID
```

- 同一预约只能关联一个有效服务记录。
- 完成后的原始护理事实不可覆盖；修正只能追加到 `service_record_correction`。
- 完成必须同时满足必填护理事实、库存可用、版本一致和幂等校验。

### 顾客确认

```text
PENDING → CONFIRMED
        └→ REJECTED
```

- 只允许绑定会员本人操作。
- 确认/反馈是独立事实，不回写或改写已完成服务状态和护理事实。
- `REJECTED` 必须有原因。

## 原子事务

完成护理的单一事务依次完成：

1. 锁定并校验服务记录与预约版本。
2. 校验技师本人范围和门店权限。
3. 写入护理事实。
4. 通过库存应用服务写入耗材领用与不可变库存流水。
5. 更新服务记录为 `COMPLETED`。
6. 由预约生命周期服务更新预约为 `COMPLETED`。
7. 创建顾客待确认事实。
8. 写审计与 outbox。

任一步失败全部回滚。故障注入已证明顾客确认写入失败时，护理、库存、预约完成和 outbox 均不残留。

## 权限与数据范围

- 管理端：门店范围 + `appointment:*`、`service_record:*`、`inventory:*` 等细分权限。
- 技师：账号必须绑定 `staff_id`，只可访问本人被分配的预约与护理记录。
- 顾客：账号必须绑定 `member_id`，只可访问本人预约、护理记录和确认。
- 追加更正要求 `service_record:correct`，不因拥有普通编辑权限而自动获得。
- 无权限或跨门店返回 403/404，不泄露其他租户实体是否存在。

## 兼容与可观测性

- V3 使用 Bearer 会话、统一响应、`X-Request-Id` 和 `Idempotency-Key`。
- V2 顾客/技师端保留现有 URL，通过适配器调用同一领域服务。
- 订单、支付、服务完成、确认和更正记录请求哈希。
- 审计和 outbox 只保存实体标识、动作和非敏感摘要，不保存手机号、健康详情、支付凭据或完整响应正文。
