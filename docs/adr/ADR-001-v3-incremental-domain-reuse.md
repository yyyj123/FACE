# ADR-001：V3.0 增量领域复用与模块边界

Status: Accepted

日期：2026-08-03

阶段：SC1

决策依据：`FACE_用户端与运营管理平台增量升级PRD_V3.0.md`、`docs/architecture/sc1-current-state-gap-audit.md`

## Context

项目已经选择“方案一：在现有系统上收缩范围并增量升级”。当前可交付面仅为响应式 H5/Web 用户端、响应式运营管理平台、统一后端，以及后续复用同一后端的微信小程序。历史总部端、分店端、技师端、采购、提成、培训等代码和数据仍作为兼容资产存在，但不属于 V3.0 新增交付范围。

SC1 审计确认现有 `backend-next` 已具备会员、预约、订单、套餐账户、售后、营销触达、通知和库存的部分能力，但存在以下结构性风险：

1. 同一业务事实存在多个候选来源，例如 `member.points` 与 `member_account` 的积分余额、`product.stock_quantity` 与 `stock_balance` 的库存余额、`care_package` 与 `package_product/package_instance` 的套餐概念。
2. `ClientPortalService`、`TransactionService`、`MemberService` 等服务直接访问其他模块表，交易规则和写入边界不统一。
3. 当前实现以 Spring JDBC、Map 投影和请求 record 为主，并非 JPA 实体体系；为 V3.0 全量改写持久化层会扩大风险且不产生直接业务价值。
4. 历史 Flyway 迁移已经构成可追溯账本，修改、重排或删除旧迁移会破坏已部署环境。
5. V3.0 仍需新增时间锁、候补、权益预占、积分批次、履约等事实，但这些新增事实不得与现有事实重复建模。

## Decision

采用“增量复用、单一事实源、模块拥有者”的架构决策：

1. **复用现有统一后端。** V3.0 继续在 `backend-next` 内演进，不新建第二套后端，不复制给微信小程序。
2. **一个事实只有一个权威模型。** 新表仅用于现有模型无法表达的新事实。会员积分以未来的积分批次/流水为账本、`member_account` 为聚合余额；库存以 `stock_balance` 与 `stock_movement` 为权威，`product.stock_quantity` 仅作兼容投影；套餐以 `package_product/package_instance` 家族为权威，`care_package` 冻结为旧兼容模型；`product` 保持 SKU 身份，未来另增 SPU 层而不复制库存。
3. **写入必须经过拥有模块。** 跨模块调用使用明确的 application port/service，不允许调用方直接写被调用模块的表。历史直写在对应阶段逐项收口，新增代码从第一天执行此规则。
4. **一个命令只有一个事务拥有者。** 订单创建、预约确认、权益核销、履约确认、售后完成等各自由一个应用服务拥有事务；事务内按文档规定的固定顺序加锁，并在同一事务写业务状态、幂等记录和 outbox 事件。
5. **跨事务传播使用 outbox。** 通知、营销触达、积分投影及其他异步副作用消费 outbox，消费者必须幂等；不得用同步跨模块多次提交模拟原子性。
6. **Flyway 只追加。** 不修改、删除或重排已应用迁移。每个阶段实施前动态读取迁移目录和 `flyway_schema_history`，重新确认下一个版本号；SC1 文档中的文件名是计划位，不是已占用版本。
7. **保留当前持久化技术。** 继续使用 Spring JDBC 和明确 SQL；本轮不以 JPA/ORM 重写为前置条件。领域边界通过应用服务、端口、事务测试和模块边界测试落实。
8. **兼容面显式冻结。** 旧接口和历史模块只有在阶段计划明确列出时才做兼容调整；不借 V3.0 删除历史表、路由或代码。

### 被否决的替代方案

- **绿地重写。** 会丢失已验证的迁移、权限、审计、支付与并发基础，且无法满足增量升级选择。
- **共享数据库自由读写。** 延续跨模块直写会使状态机、锁顺序、回滚和审计无法证明正确。
- **为 V3.0 复制一套 `v3_*` 业务表。** 会造成会员、订单、库存和套餐双账，迁移和对账成本不可控。
- **先统一改写为 JPA 再做业务。** 技术替换与当前交付目标无直接关系，风险和范围均过大。

## Consequences

### 正向结果

- 后续 H5、运营平台和微信小程序共享同一业务规则和事实源。
- 状态流转、幂等、锁和 outbox 可在单一事务边界内验证。
- 历史数据和 Flyway 校验和保持可追溯，新增字段/表可以分阶段回填与切换。
- SC2 至 SC10 均可用文件级计划和模块边界测试约束范围。

### 成本与约束

- 在新增能力前，需要在相应阶段先收口 `ClientPortalService`、`TransactionService`、`MemberService` 等已识别的跨模块直写。
- 兼容投影会暂时保留，但只能由权威模块同步，不能继续成为写入入口。
- 新迁移需采用“新增可空结构 → 可重跑回填 → 对账 → 切读 → 约束收紧”的渐进方式，阶段数量会增加。
- SC1 只作决策和计划，不代表时间锁、优惠券、积分批次、履约等能力已经实现。

### 强制实施门禁

后续每个阶段进入编码前必须证明：

1. 没有为已有事实新增第二个权威模型；
2. 新写路径不直接修改其他模块拥有的表；
3. 迁移为追加式且已通过动态 `migrate`、`validate` 和历史表检查；
4. 状态变化、幂等键、锁顺序、outbox 和失败回滚均有自动化测试；
5. 阶段完成后停止，等待下一阶段人工放行。
