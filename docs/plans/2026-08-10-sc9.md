# SC9 生产部署准备实施计划

日期：2026-08-10
阶段：SC9
产品基线：`docs/specs/FACE_用户端与运营管理平台增量升级PRD_V3.0.md` 方案一
上一阶段基线：`sc8/v1.0.0` / `c09c978afc2d98f8132956264ab806071a6d7f7e`

## 目标与边界

本阶段只交付生产部署准备：Linux Docker Compose、正式 TLS 入口结构、Docker Secret/配置树隔离、S3 兼容对象存储、数据库与对象存储备份恢复、Prometheus/Alertmanager 监控告警、外部支付/短信/物流适配器安装机制，以及可执行的 Go/No-Go 门禁。

生产公开入口只包含 `/client/`、`/admin/` 和 `/api/`；不得启动或公开独立技师端。生产环境必须显式使用 `prod` Profile，拒绝固定验证码、`DEMO_MOCK`、支付 Sandbox 和任何 DEMO 自动降级。真实渠道供应商尚未选定，因此本阶段只提供安装、校验和证据门禁，不伪造真实支付、短信或物流成功，不使用真实客户数据或生产密钥。

不进入 SC10；不创建微信小程序页面、微信身份绑定、分享、订阅消息或小程序支付适配。现有业务状态机、资产流水和历史迁移不修改。

## 已确认差距

1. `compose.yaml` 面向本地/B0 验收，直接发布 backend/admin/client/technician 端口，技师服务仍作为兼容资产启动。
2. 数据库和渠道密钥由环境变量传递，没有生产 Secret 文件或 Spring Config Tree 契约。
3. 没有统一 TLS 网关、正式域名配置、HTTP→HTTPS 跳转和安全响应头。
4. 没有对象存储服务、固定 bucket 初始化或对象存储健康门禁。
5. 只有数据库 dump 脚本雏形，没有生产备份清单、SHA-256、对象备份和隔离恢复演练。
6. 后端暴露基础 Actuator health/metrics，但没有 Prometheus registry、告警规则或 Alertmanager。
7. 支付已有 `PaymentChannelAdapter`、DEMO 与 Sandbox；短信已有 demo/disabled/http 适配器；物流没有统一安装契约。生产没有阻止 DEMO/Sandbox 降级或要求渠道验收证据的启动门禁。
8. 没有 Linux 一键启动/停止脚本、显式端口预检、生产配置静态检查或 Go/No-Go 汇总。

## 实施任务

1. 先新增失败契约 `scripts/test-sc9-production-contract.ps1`，覆盖生产 Compose、TLS、Secret、对象存储、监控告警、Linux 脚本、生产 Profile、渠道安装证据和无技师公开服务；确认当前仓库失败。
2. 新增 `docker-compose.prod.yml`、`.env.prod.example` 和 `.env.prod.test`。生产 overlay 只发布统一网关的显式 HTTP/HTTPS 端口；backend、MySQL、MinIO、Prometheus、Alertmanager 均仅在内部网络；冻结技师服务置于不可默认启用的 profile。
3. 新增 `prod/gateway/`：Nginx 使用 Secret 挂载的证书和私钥，在容器内非特权端口提供 TLS，HTTP 只做 HTTPS 跳转；反代 `/client/`、`/admin/`、`/api/`，拒绝 `/technician/`，设置 HSTS、CSP、frame、MIME、referrer 等生产头。
4. 将数据库口令、TLS 私钥、对象存储口令、短信令牌和可选告警 webhook 改为 Docker Secret/Config Tree 文件注入。MySQL 使用官方 `_FILE` 变量；后端通过 `SPRING_CONFIG_IMPORT=configtree:/run/secrets/` 读取，不在 Compose 渲染、命令行或日志输出 Secret。
5. 增加仅 `prod` Profile 激活的生产安全门禁及测试：启动时拒绝 `demo` Profile、固定验证码、`DEMO_MOCK`、Sandbox 支付密钥、缺失对象存储、缺失强 Secret、未校验的外部适配器或不完整渠道证据。生产未启用真实渠道时保持 disabled，不改变业务事实。
6. 增加外部适配器安装机制：后端通过 Spring Boot `PropertiesLauncher` 从只读 `/app/adapters` 加载受信 JAR；支付、短信、物流按显式模式启用。每个非 disabled 渠道必须有适配器 SHA-256 清单和验收证据；支付要求 Sandbox、小额支付、退款、对账四项 PASS，短信和物流要求各自 Sandbox 与回执/轨迹验证。未提供实际供应商 JAR 时不得启用。
7. 新增 S3 兼容 MinIO 生产服务、bucket 初始化和后端 readiness 健康检查。对象存储不公开控制台端口；应用只接收内部 endpoint 和受控公开基础 URL。备份同时覆盖 MySQL 与对象 bucket。
8. 为后端加入 Prometheus registry；新增 `prod/monitoring/` 的 Prometheus scrape、告警规则和 Alertmanager 配置。至少覆盖后端不可用、readiness 失败、JVM 堆高水位和备份过期；监控端口不公开，验收通过容器内 API 检查规则和目标。
9. 新增 Linux `scripts/prod-start.sh`、`prod-stop.sh`、`prod-backup.sh`、`prod-restore-drill.sh`、`prod-go-no-go.sh`。启动前检查 Linux 引擎、Docker/Compose、固定端口占用、Secret 文件权限、证书有效期、Compose 配置和渠道证据；禁止随机端口。恢复演练只操作显式命名的隔离验收 project/volume。
10. 新增 `scripts/verify-sc9-runtime.ps1` 作为当前工作站的正式验收编排：在 Docker Linux engine 上校验 Linux shell、构建、Flyway `migrate`/`validate`/目录历史动态一致性、TLS、Secret 不泄露、对象存储、监控、渠道拒绝门禁、备份恢复、重启和 Go/No-Go。使用两个独立 project 连续从干净状态运行两轮。
11. 在 `docs/verification/SC9/` 留存候选 SHA、tag、环境版本、命令、两轮日志、TLS/监控/备份恢复/门禁证据、风险和来源限制；更新 `README.md`、`PRODUCT.md`、`CONTRIBUTING.md` 与生产运维文档。

## 测试优先顺序

1. 运行 `scripts/test-sc9-production-contract.ps1`，记录生产文件和门禁缺失的预期失败。
2. 为生产安全门禁、对象存储健康和渠道证据校验先写 Java 单元测试，确认失败后实现最小代码。

5. 两次执行 SC9 正式运行验收；任何代码、Compose 或脚本修正后，两轮均从 Run 1 重新开始。

## 验收与停止条件

- Docker 引擎为 Linux；生产 Compose 在独立、干净 project 中可重复构建、迁移、启动、健康检查、重启和停止。
- TLS 入口有效，HTTP 跳转 HTTPS；只有用户端、运营端和统一 API 可见，独立技师端不可访问。
- Secret 不出现在 Git 跟踪文件、`docker compose config`、进程参数、应用日志或验收日志；示例仅描述生成方法。
- Flyway 继续使用 `migrate`、`validate`、迁移目录和 `flyway_schema_history` 动态一致性，不新增或修改业务迁移。
- 数据库与对象存储备份生成清单和 SHA-256；隔离恢复后数据库指纹、迁移历史和对象指纹一致。
- Prometheus target、告警规则和 Alertmanager 健康；后端 readiness 与对象存储健康进入 Go/No-Go。
- `prod` Profile 无固定验证码、无 `DEMO_MOCK`、无 Sandbox 密钥；缺少渠道 JAR、SHA 或验收证据时启动/门禁明确失败。所有外部渠道 disabled 时允许平台上线但明确不可用，不做模拟降级。
- 两轮均通过后提交 SC9 实现和证据，创建 `sc9/v1.0.0` 标签，立即停止并等待人工回复“通过，进入 SC10”。
