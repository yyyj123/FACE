# FACE 美容院店铺管理系统——技师端产品设计方案 V1.1

> 状态：建议评审稿  
> 目标版本：V2 技师服务闭环 MVP  
> 适用端：`front-next` 中的 `BEAUTICIAN` 角色体验  
> 修订原则：先保证本人服务闭环、数据一致和隐私安全，再扩展套餐、提成与运营能力

## 1. 执行摘要

### 1.1 产品决策

技师端首期不建设成独立的“门店员工全功能后台”，而是在现有 `front-next` 中提供按角色裁剪的移动工作台。

首期只解决一个核心问题：

> 当班技师如何在手机上，把“分配给我的已到店预约”安全、快速、可追溯地转化为完整服务记录、护理档案和耗材流水，并避免前台代录、越权查看、重复完成和重复扣库。

首期主路径为：

```text
本人日程
→ 查看当前/下一项任务及必要客户风险
→ 开始服务
→ 记录服务结果与实际耗材
→ 完成服务或上报异常
→ 留痕并交接前台
```

### 1.2 立项结论

- 批准“技师服务闭环 MVP”进入详细设计。
- 不批准 V1.0 全功能清单直接进入开发。
- 套餐/次卡、自动提成、考勤、培训、设备管理等保留为长期能力地图，不进入 P0。
- P0 上线前必须修复两项阻断问题：
  1. 禁止技师通过通用预约状态接口直接把预约改为 `COMPLETED`。
  2. 服务记录、客户历史和护理详情必须按当前技师 `staff_id` 强制收口。

## 2. 问题定义

### 2.1 用户问题

门店技师在连续服务、双手被占用和网络不稳定的场景下，缺少一个低摩擦入口来：

- 判断现在该服务谁、下一位是谁；
- 查看与本次服务直接相关的客户风险和偏好；
- 快速记录实际护理结果和耗材；
- 在中断、超时、重复点击或数据冲突时安全恢复。

结果是预约状态、护理档案和耗材由多人事后补录，容易出现遗漏、越权、重复扣库和责任不清。

### 2.2 业务结果

- 降低前台代录率和服务后补录率。
- 提高预约到完整服务记录的闭环率。
- 保证预约、护理档案、耗材流水和库存余额一致。
- 将客户资料限制在“本人当前或历史服务关系”范围内。
- 为未来客户确认、套餐核销、售后和提成提供可信事实源。

### 2.3 一句话价值主张

FACE 技师工作台帮助当班技师在几分钟内完成从预约到护理档案和耗材记录的闭环，无需跨系统或依赖前台补录，同时保证每次服务可追溯、库存不重复扣减、客户隐私不越权。

## 3. 用户与协作边界

### 3.1 主用户

**单店当班技师**

- 主要使用手机；
- 一天连续处理多笔预约；
- 最关心当前任务、下一位客户、风险和快速收尾；
- 只需要本人任务和与服务有关的客户资料，不需要全店 CRM。

### 3.2 协作角色

| 角色 | 主要职责 | 不应承担 |
|---|---|---|
| 前台 | 预约、改期、签到、结算、联系客户 | 代替技师填写护理内容 |
| 店长 | 改派、异常决策、敏感信息授权、记录修订审批 | 无痕修改技师记录 |
| 技师 | 执行本人服务、填写记录与耗材、上报异常 | 查看全店客户、直接处理支付退款 |
| 顾客 | 后续确认、评价或提出争议 | 成为 P0 服务事实落账的强依赖 |

### 3.3 使用场景

技师在门店室内移动操作，服务过程中双手经常被占用，关注时间短且可能被客户或同事打断。界面默认使用现有浅色主题和玫瑰主操作色，强调清晰、低干扰、单手可达与中断恢复。

## 4. 产品目标与成功指标

### 4.1 北极星指标

**当日服务闭环率**

```text
当日形成“已完成服务单 + 护理档案 + 应记耗材流水”的预约数
÷ 当日实际完成服务预约数
```

- 单店试点 30 天目标：≥ 90%
- 稳定期目标：≥ 95%

目标值需在 M0 获得真实基线后最终确认。

### 4.2 行为指标

- ≥ 85% 的本人预约由技师本人推进服务，而非前台代操作。
- 服务结束到记录提交的中位耗时 ≤ 3 分钟。
- 已完成服务中护理档案缺失率 < 5%。
- 应记录耗材的服务中，耗材记录完整率 ≥ 95%。
- 排班技师周活跃率 ≥ 80%。
- 标准无异常服务中，至少 80% 字段由预约、项目或过程记录自动生成。

### 4.3 质量与护栏

- 跨租户、跨门店、跨技师越权成功数：0。
- 重复服务单、重复库存扣减数：0。
- 完成服务接口错误率 < 1%。
- 预约状态与服务单不一致率 < 0.5%。
- 版本冲突不得静默覆盖任一方数据。
- 离线或超时不得向用户展示虚假成功。

不使用页面访问量、点击量或“上线功能数”衡量成功。

## 5. 范围与优先级

### 5.1 P0：单店试点必备

| 能力 | P0 范围 |
|---|---|
| 身份与范围 | `BEAUTICIAN` 登录；本人排班、预约、服务记录；门店授权校验 |
| 今日工作台 | 当前服务、下一位、今日时间轴、阻塞待办 |
| 日程与预约 | 本人今日/近期预约、详情和状态说明 |
| 客户信息 | 称呼、项目、必要备注、过敏/禁忌；手机号默认脱敏 |
| 开始服务 | 仅本人且为 `CHECKED_IN` 的预约可开始 |
| 服务记录 | 服务结果、客户反应、护理建议、实际耗材 |
| 完成事务 | 护理档案、耗材、库存流水、服务单和预约同事务完成 |
| 最小异常 | 客户不适、无法继续、产品/设备问题；原因必填并通知处理人 |
| 防错恢复 | 本地草稿、幂等提交、乐观锁、重复点击防护、冲突恢复 |
| 审计监控 | 敏感资料访问、开始、完成、异常、耗材操作留痕 |
| 系统状态 | 加载、空数据、无权限、弱网、超时、冲突、部分失败 |

P0 不引入“待接订单池”。当前 V2 在预约创建时已分配技师，是否需要二次接单尚无用户证据。

### 5.2 P1：试点验证后的运营增强

- 项目级标准服务步骤和必填项配置。
- 结构化过敏、禁忌和服务偏好。
- 服务前后照片及受控查看。
- 客户确认或经理豁免。
- 加项申请与前台审批。
- 转单、暂停和中止。
- 回访任务、消息和异常进度。
- 仪器故障上报。
- 服务记录修改申请及版本审批。

### 5.3 P2：平台扩展

- 套餐/次卡核销、换项和反向核销。
- 业绩、提成、退款冲减和申诉。
- 考勤、请假、换班。
- 培训、考试、证书和资格生命周期。
- 仪器预约与维护。
- 多技师协作、跨店支援和共享技师。

### 5.4 当前非目标

- 储值卡、套餐/次卡和自动提成。
- 在线支付、短信、公众号和自动营销集成。
- 全店客户搜索、批量导出和完整财务信息。
- 客户确认后才能记录服务事实。
- 完整离线业务处理；P0 只支持草稿保留与安全重试。
- 月视图、复杂日历和经营 BI。

## 6. 信息架构

### 6.1 移动端底部导航

```text
工作台｜日程｜服务｜我的
```

设计理由：

- “预约”对技师本质是个人日程，不是完整预约管理中心。
- 客户资料从预约和服务上下文进入，避免无业务目的地浏览客户。
- 耗材、异常和加项嵌入当前服务，不设一级菜单。
- 排班、历史、消息和后续个人能力统一收纳到“我的”。

### 6.2 导航规则

- 一级页面持续显示底部栏；服务执行等沉浸流程隐藏底部栏。
- 图标与文字同时显示，触控目标建议至少 48 × 48 px。
- 返回时保留列表筛选、滚动位置、当前服务步骤和未提交文本。
- 未同步草稿和待处理异常使用数字角标，不闪烁。
- 一屏只保留一个高优先级主按钮。

## 7. 核心页面

### 7.1 工作台

首屏按以下优先级组织：

1. 当前服务：一个“继续服务”主按钮；
2. 下一位客户：时间、称呼、项目、房间、首次到店和风险；
3. 今日时间轴；
4. 阻塞待办：异常、超时、待补记录、同步失败；
5. 个人摘要，放在首屏之后。

不在工作台直接提供“完成服务”，必须进入服务页完成校验。

### 7.2 预约详情

展示：

- 时间、门店、项目和预计时长；
- 客户称呼和最小必要联系方式；
- 与本次护理直接相关的过敏、禁忌和偏好；
- 当前状态、前置条件和可执行主动作；
- 前台或店长留下的业务备注。

禁止：

- 查看客户完整财务流水；
- 探索同店其他客户；
- 未授权展示完整手机号。

### 7.3 服务前确认

- 身份、项目和已有档案自动带入。
- 过敏和禁忌置顶，必须逐项确认。
- 无变化可选择“与档案一致”；有变化时展开补充。
- 实际开始时间由系统记录。
- 按钮禁用时说明缺少的条件及责任人。

### 7.4 服务执行

页面骨架：

```text
客户称呼｜项目｜已服务时长｜同步状态
风险提醒
当前步骤 / 总步骤
当前动作、标准产品/仪器、必要记录
上一步｜完成本步骤 / 下一步
更多：暂停、异常、联系前台
```

交互要求：

- 默认只展开当前步骤。
- 标准用量和参数预填，技师只记录实际偏差。
- 每个步骤变更后本地保存草稿。
- 异常入口始终可达，但不与主操作同权重。
- P0 若尚无项目步骤模板，采用单页最小记录，不虚构复杂 SOP。

### 7.5 服务完成

字段分为：

- 系统生成：开始、结束、时长、项目、技师、耗材选择结果；
- 技师必填：服务结果、客户反应；
- 条件必填：异常、超量或中止原因；
- 推荐填写：护理建议、下次到店建议；
- 项目配置：照片、测量值等，进入 P1。

提交摘要必须区分：

- 已完成；
- 缺少且阻塞提交；
- 可稍后补充。

P0 的服务完成不得依赖客户确认。客户确认在 P1 作为独立证据状态设计。

### 7.6 异常上报

技师可在两次操作内发起：

- 客户不适或要求中止；
- 产品、库存或设备问题；
- 预约信息与现场不一致；
- 需要店长或前台处理的其他情况。

高风险异常创建后冻结完成操作，由店长决定继续、终止或改派；所有决定记录身份、时间、原因和版本。

## 8. 状态模型

各业务聚合必须独立建模，不能把预约、服务、确认、支付和售后塞进一条状态轴。

| 聚合 | 状态 |
|---|---|
| Appointment | `PENDING`, `CONFIRMED`, `CHECKED_IN`, `IN_SERVICE`, `COMPLETED`, `CANCELLED`, `NO_SHOW` |
| Service record | `IN_PROGRESS`, `COMPLETED`, `VOID` |
| Confirmation（P1） | `PENDING`, `CONFIRMED`, `WAIVED`, `DISPUTED` |
| Order | `UNPAID`, `PARTIALLY_PAID`, `PAID`, `VOID` |
| Refund | `PENDING_REVIEW`, `APPROVED`, `REJECTED`, `COMPLETED` |
| Exception | `OPEN`, `INVESTIGATING`, `RESOLVED`, `CLOSED` |
| Offline draft | `DRAFT`, `QUEUED`, `SENDING`, `ACKED`, `CONFLICT`, `FAILED_PERMANENT` |

“暂停服务”先作为事件和计时段，不扩充服务主状态。只有未解决的高风险异常才阻止完成。

### 8.1 正常路径

```text
前台确认预约
→ 前台签到客户
→ 技师开始服务
→ 创建唯一 IN_PROGRESS 服务单
→ 技师填写服务草稿
→ 技师提交完成
→ 同事务写护理档案、扣服务耗材、写库存流水
→ 服务单及预约变为 COMPLETED
→ 前台创建唯一订单并结算
```

P1 引入客户确认后：

```text
服务完成
→ confirmation=PENDING
→ 客户确认或经理带理由豁免
→ 进入后续结算/争议处理
```

客户确认不应阻塞真实服务事实和耗材事实的落账。

## 9. 交接与异常恢复

### 9.1 跨角色交接

- 前台负责签到，技师不能跳过 `CHECKED_IN` 直接开始。
- 技师负责服务事实，前台不能代填护理内容。
- 店长负责改派和高风险异常决策，所有覆盖操作必须审计。
- 前台结算只能基于已完成服务生成唯一订单。

### 9.2 库存不足

- 整个完成事务回滚；
- 服务保持 `IN_PROGRESS`；
- 不产生孤立护理档案或库存流水；
- 刷新库存版本、修正用量后使用原业务意图重试。

### 9.3 网络中断与超时

- 步骤、文字和数值允许加密保存为本地草稿。
- 开始、完成、结算、退款和核销等不可逆命令必须联网。
- 超时后使用持久化幂等键查询原结果，不生成新键盲目重试。
- 界面明确显示“已保存到本机”“同步中”“同步失败”或“已同步于 HH:mm”。
- 错误信息必须说明：发生了什么、内容是否已保存、下一步怎么做。

### 9.4 版本冲突

- 显示服务器变化摘要；
- 保留本次输入；
- 允许重新加载或复制补充内容；
- 禁止静默覆盖。

## 10. 数据一致性与安全规则

### 10.1 上线阻断规则

1. 技师不能通过预约状态接口直接提交 `IN_SERVICE → COMPLETED`。
2. “完成服务”只能调用服务护理完成命令。
3. 技师只能读取、开始和完成分配给自己的预约与服务。
4. 开始服务时重新校验门店授权、技师资格、预约归属和版本。
5. 完成服务、护理档案、耗材流水、库存余额和预约状态同事务成功或全部回滚。
6. 同一预约最多一个服务单、一个结算订单。
7. 同一幂等键和请求指纹重复提交返回同一结果；同键不同负载返回冲突。
8. 服务耗材只在服务完成时扣库；零售商品只在订单最终支付时扣库。
9. 退款不自动回库；实物验收后另记退货入库流水。
10. 已完成护理档案不得无痕覆盖。

### 10.2 隐私

- 服务 API 必须从 token 解析当前 `staff_id`，不能信任前端传入的技师 ID。
- 技师只能从本人预约、本人历史服务或限时授权进入客户资料。
- 手机号默认脱敏；不提供完整客户导出。
- 客户照片禁止批量下载，P1 展示时应增加可追溯水印。
- 敏感资料访问记录技师、客户、门店、时间、用途和结果。
- 权限撤销后，本地草稿和缓存必须不可继续读取。
- 推送和任务卡不显示完整姓名、手机号、过敏详情或照片。

## 11. 现有 V2 复用边界

P0 必须复用现有领域模型和服务，不新建重复的“技师端专用业务表”。

| 业务概念 | 复用对象 |
|---|---|
| 账号与角色 | `account` |
| 员工与门店 | `staff`, `staff_shop_assignment` |
| 排班 | `staff_schedule` |
| 预约 | `appointment` 及状态历史 |
| 服务 | `service_record`, `service_record_item` |
| 护理档案 | `care_record` |
| 服务耗材 | `service_record_consumption` |
| 库存事实 | `inventory_movement` |
| 结算 | `sales_order` |
| 追溯 | 现有审计日志与版本字段 |

### 11.1 当前实现缺口

- `front-next` 当前技师端主要操作预约状态，尚未完整接入服务护理 API。
- 通用预约状态接口允许技师绕过护理档案直接完成。
- 服务记录列表、详情和会员历史需补充技师本人范围。
- 完成幂等需保存请求指纹，识别“同键不同负载”。
- 订单唯一性应由数据库约束或幂等命令保证。

## 12. 非功能与体验要求

### 12.1 移动端与可访问性

- 360 px 宽度下核心任务无横向滚动。
- 触控目标建议至少 48 × 48 px。
- 正文对比度不低于 4.5:1，大字不低于 3:1。
- 系统字号放大至 200% 时不截断、不遮挡主操作。
- 状态和错误不只依赖颜色。
- 表单使用持久标签，不以占位符替代标签。
- 支持屏幕阅读器和可见键盘焦点。
- 动效只表达状态，150–250 ms，并支持减少动态效果。

### 12.2 交互效率

- 从工作台继续当前服务不超过 1 次点击。
- 从工作台开始下一位服务不超过 2 次点击。
- 技师无需手填开始、结束和总时长。
- 标准耗材用量每项不超过 2 次操作。
- 提交后立即反馈并防止重复点击。

### 12.3 系统状态

所有 P0 页面需设计并验收：

- 加载骨架；
- 有解释和下一步的空状态；
- 无权限；
- 网络不稳定与离线草稿；
- 登录过期；
- 409 版本冲突；
- 422 业务校验；
- 超时与 500；
- 部分上传失败；
- 本地空间不足。

## 13. P0 验收标准

### 13.1 主流程

- 本人 `CHECKED_IN` 预约可开始服务并创建唯一 `IN_PROGRESS` 服务单。
- 非本人、跨门店和跨租户预约全部拒绝。
- 完成提交后，护理档案、耗材流水、库存余额、服务单和预约状态一致。
- 任一子操作失败时整体回滚，服务仍可恢复。
- 服务完成后可由前台生成唯一未支付订单。

### 13.2 防错与恢复

- 重复点击和超时重试不产生重复服务单或重复扣库。
- 同键不同负载返回明确冲突。
- 网络断开或应用重启后，最近草稿和步骤位置可恢复。
- 不可逆操作在未收到服务端确认前不显示成功。
- 错误后保留所有已输入内容。

### 13.3 权限与隐私

- 技师不能检索或查看同店其他技师的客户和护理历史。
- 手机号和敏感财务信息默认不完整展示。
- 每次敏感访问和经理覆盖操作可审计。
- 权限撤销后在线和离线缓存均不可继续访问。

### 13.4 一致性

- 技师不存在直接完成预约的旁路。
- 预约与服务状态不可越级跳转。
- 库存不足或版本冲突时不产生孤立档案或流水。
- 已完成记录的后续修改有明确修订痕迹。

## 14. 交付计划

### M0：问题验证与范围锁定，2–3 个工作日

- 观察至少 5 名技师完成真实服务；
- 访谈 2 名前台或店长；
- 取得闭环率、代录率、补录率和填写耗时基线；
- 确定 P0 必填字段和低风险试点项目；
- 输出范围签字版与“不做清单”。

退出门槛：主路径、字段和试点人群达成一致。

### M1：权限与契约硬化，第 1 周

- 服务记录按 `staff_id` 收口；
- 阻断跨技师查看、开始、完成和客户历史访问；
- 完成入口统一走服务护理事务；
- 补齐幂等、版本冲突和跨范围测试。

退出门槛：安全用例全部通过，无法再生成“预约完成但护理待补”的技师记录。

### M2：核心技师体验，第 2 周

- 工作台、本人日程、预约详情、服务前确认和开始服务；
- 明确加载、空状态、异常与恢复；
- 移动端草稿保留与重复操作防护。

退出门槛：技师可独立完成“签到后开始服务”。

### M3：服务完成闭环，第 3 周

- 服务结果、客户反应、护理建议和耗材表单；
- 原子完成、请求指纹、幂等和乐观锁；
- 最小异常上报；
- 指标和审计可查询。

退出门槛：服务、档案和库存任一失败均整体回滚，重复提交不重复扣库。

### M4：单店封闭试点，第 4 周

- 1 家门店、5–10 名技师、限定低风险项目；
- 每日检查闭环率、填写耗时、错误率和越权日志；
- 修正必填字段和异常流程。

放量门槛：

- 闭环率 ≥ 90%；
- 越权与重复扣库均为 0；
- 中位填写耗时 ≤ 3 分钟；
- 无 P0/P1 级数据一致性问题。

### M5：分批推广，第 5–6 周

- 20% 门店 → 50% → 100%；
- 每阶段至少观察 3 个营业日；
- 未达门槛则暂停扩量；
- 不在推广期同时引入套餐、提成或客户确认。

## 15. 关键风险与待确认问题

| 问题 | 当前建议 |
|---|---|
| 技师是否需要接单/拒单？ | P0 不做，先验证预约已分配模式 |
| 谁负责客户签到？ | 前台 |
| 客户确认是否阻塞完成？ | 不阻塞服务事实；P1 独立设计 |
| 项目级必填项如何配置？ | P0 最小通用字段，P1 模板化 |
| 完成后如何修改护理档案？ | 必须留修订记录；是否需经理审批待确认 |
| 弱网要支持到什么程度？ | P0 仅草稿与安全重试，不离线执行不可逆命令 |
| 库存批次是否首期必须？ | 结合试点项目风险决定，现有 V2 尚未完整支持 |
| 技师资格何时校验？ | 预约时和开始服务时均校验 |

## 16. 相比 V1.0 的关键变化

| V1.0 | V1.1 |
|---|---|
| 技师端承载多个业务中心 | 首期聚焦本人服务闭环 |
| 大而全的桌面后台菜单 | 移动端四项任务型导航 |
| 套餐、提成、考勤、培训进入早期范围 | 明确移至 P2 或当前非目标 |
| 单一状态机串联服务、确认、支付、售后 | 按业务聚合拆分状态 |
| 客户确认阻塞完成 | 服务事实先完成，确认作为独立证据 |
| 强调页面和字段完整 | 强调三分钟完成、自动带入与异常优先 |
| 宣称完整离线闭环 | P0 只承诺草稿恢复和安全重试 |
| 新建一套技师端数据表 | 复用 V2 预约、服务、护理、库存和订单模型 |
| 功能验收为主 | 增加越权、并发、幂等、回滚和放量门槛 |

## 17. 下一步决策

在进入 UI 详细设计和开发前，需要完成以下决策：

1. 业务确认 P0 必填字段和试点服务项目；
2. 技术确认移除技师直接完成预约的旁路；
3. 安全确认服务和客户数据按当前 `staff_id` 收口；
4. 门店提供 5 名技师和 2 名前台/店长参与 M0；
5. 产品、技术和门店共同签署 P0“不做清单”。

若以上条件未满足，不建议开始套餐、提成、客户确认或全量页面开发。
