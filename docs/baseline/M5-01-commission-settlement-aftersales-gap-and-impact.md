## 2. 基线结论与冲突处理

### 2.1 四份文档共同要求

M5 必须交付：

1. 提成规则版本、适用范围和计算快照。
2. 提成入账、冻结、解冻、结算和退款冲正。
3. 历史规则与历史提成结果可复现，禁止按当前规则覆盖历史结果。
4. 售后工单、通用审批实例、职责分离、权限和审计。
5. 面向相关角色的站内通知及已读状态。
6. 提成、退款、结算和审批的租户/门店/SELF 范围校验。
7. 数据库事务、唯一约束、版本、幂等、不可变流水、outbox 和敏感数据保护。

M5 退出条件为：

- 历史订单按快照规则可复现。
- 退款成功会追加提成冲正，不修改原提成记录。
- 未结算、已冻结、已结算三种情况下的退款均有确定处理。
- 审批越权和跨门店/跨租户访问为零。
- 测试、构建、迁移、运行验证及文档同步全部通过。

### 2.2 文档缺口

V1.2 已明确 M5 的目标表为 `commission_rule_version`、`commission_entry`、
`after_sale_case` 和 `approval_instance`，但商业 API 文档尚未列出 M5 路由，数据库
文档也未给出全部字段、索引和结算明细结构。

处理原则：

- 不猜测或改变 `/api/v1`、`/api/v2` 行为。
- M5 新能力统一使用 `/api/v3`，先由
  `docs/architecture/api-contract-m5.md` 固化契约。
- 在 M5-07 将已验收契约同步进下一版四份商业文档。
- 表结构只允许 Flyway 向前扩展，最终字段以失败测试、迁移评审和真实 MySQL 8
  验证为准。

### 2.3 “重算”与“不可覆盖历史”的表面冲突

PRD 的退出条件写有“重算、冲正和权限通过”，API 文档同时明确禁止“历史订单按当前
规则重算并覆盖”。两者不冲突，保守解释如下：

- “重算”仅用于基于原规则版本快照进行校验或形成独立模拟结果。
- 已入账提成不得原地改金额、规则版本、归属员工或来源事实。
- 纠错、退款和追补只追加 `ADJUSTMENT` 或 `REVERSAL` 流水并引用原提成。
- 模拟重算结果不得自动入账，必须通过审批和显式确认。

### 2.4 结算范围的补充

V1.2 实施文档建议 M5 以“员工提成、结算、工资/财务核对”为主线，但目标表清单未包含
结算表。为满足可核对和不可变历史要求，M5 受控新增
`commission_settlement_batch` 与 `commission_settlement_item`：

- 只结算已冻结且未结算的提成流水。
- 结算明细保存提成流水引用和结算时金额，不复制或覆盖原提成。
- 已结算后的退款追加负向冲正，并进入下一批结算，不回写已关闭批次。
- 本阶段不实现完整人事薪资、个税或银行代发；这些属于外部薪资系统边界。

| 范围 | 当前实现 | M5 要求 | 处理 |

| 提成流水 | 不存在 | 来源快照、员工归属、金额、冻结、冲正、结算 | 新增追加式 `commission_entry` |

| 审批 | 退款/采购分别内嵌审批 | M5 通用审批实例与步骤 | 新增 `approval` 模块，旧流程暂不强迁 |
| 通知 | 无业务站内通知模型 | 待审批、处理结果和提成/结算通知 | 新增最小站内通知模块 |

| 技师端 | 已有本人工作台和服务履约 | 本人提成、结算和售后协作 | 仅 SELF 投影，不暴露规则维护和他人金额 |
| 会员端 | 已有本人退款进度 | 本人售后工单和通知 | 仅 SELF，隐藏内部提成与审批意见 |

## 4. 影响模块与所有权

### 4.1 `commission` 提成模块

- 独占规则版本、规则适用范围和提成不可变流水。
- 从护理完成、支付成功和退款完成等公开事实计算结果。
- 每条提成保存来源事实、规则版本、计算基数、计算参数快照、金额和归属员工。
- 规则发布后不可修改；变更必须创建新版本并设置新的生效区间。
- 原提成不可删除或覆盖；冲正引用原流水，金额方向相反。

### 4.2 `settlement` 结算模块

- 独占结算批次和结算明细。
- 只引用可结算提成流水，不直接更新订单、支付、退款或护理记录。
- 批次关闭后不可重开或修改明细。
- 已结算后发生退款时，负向提成冲正进入后续结算批次。
- 财务核对只记录差异、原因和解决轨迹，不直接抹平。

### 4.3 `aftersale` 售后模块

- 独占售后工单、跟进记录、处理方案和状态历史。
- 可引用订单、支付、退款、服务记录和会员，但不直接写这些模块私有表。
- 涉及退款时调用退款应用服务；涉及套餐/账户时调用相应冲正应用服务。
- 工单关闭后更正只能追加记录或重开新工单。

### 4.4 `approval` 审批模块

- 独占审批实例、步骤、决定和审批历史。
- 业务模块创建审批实例并保存业务对象类型/标识，不复制敏感业务正文。
- 决定完成后通过应用服务回调或 outbox 通知业务模块。
- 申请人与最终审批人必须职责分离；超额、跨门店和跨租户均拒绝。
- M5 不强行迁移已经稳定的退款和采购历史审批，只为新增 M5 流程和后续渐进适配提供边界。

### 4.5 `notification` 通知模块

- 独占站内通知、接收人、已读时间和去重键。
- 只保存必要业务标识和安全摘要，不保存手机号、健康信息、支付凭据或完整售后正文。
- 邮件、短信和企业微信属于外部通道，未配置时不能伪造“已发送”。

### 4.6 现有模块协作

- `servicecare`：发布 `ServiceRecordCompleted`，不写提成表。
- `transaction/payment`：发布 `PaymentSucceeded`；退款成功通过公开冲正端口或
  `RefundCompleted` 事件联动提成。
- `packageaccount`：按自身边界完成套餐/账户冲正，不写售后或提成私有表。
- `outbox`：继续提供至少一次投递；M5 消费者必须使用业务唯一键实现幂等。
- `security`：继续统一校验租户、门店、角色、权限和 SELF 范围。

## 5. 计划表、索引与约束

### 5.1 计划新增表

| 表 | 用途 | 关键不可变/并发要求 |
|---|---|---|
| `commission_rule_version` | 已发布提成规则版本 | 发布后不可改；租户/规则号/版本唯一 |
| `commission_rule_scope` | 规则适用门店、角色、员工、项目或商品范围 | 同版本同范围去重 |
| `commission_entry` | 提成入账、调整和冲正流水 | 来源事实/员工/类型唯一；原流水引用 |
| `commission_settlement_batch` | 门店/周期结算批次 | 租户/门店/周期/批次号唯一；乐观锁 |
| `commission_settlement_item` | 结算明细 | 一个可结算提成流水最多进入一个有效批次 |
| `after_sale_case` | 售后工单主数据 | 租户内工单号唯一；版本字段 |
| `after_sale_case_log` | 追加式跟进和状态记录 | 只追加，不覆盖 |
| `approval_instance` | 审批实例 | 业务对象/审批类型/有效实例唯一 |
| `approval_step` | 审批步骤和决定 | 步骤序号唯一；决定后不可修改 |
| `notification_message` | 站内通知 | 接收人/业务事件/去重键唯一 |

### 5.2 必要索引

- 规则：`(tenant_id, rule_code, version_no)` 唯一；
  `(tenant_id, status, effective_from, effective_to)` 查询索引。
- 提成：`(tenant_id, source_type, source_id, staff_id, entry_type)` 唯一；
  `(tenant_id, shop_id, staff_id, status, occurred_at)` 查询索引；
  `original_entry_id` 索引。
- 结算：`(tenant_id, shop_id, settlement_no)` 唯一；
  `(tenant_id, shop_id, period_start, period_end, status)` 查询索引；
  有效结算明细的 `commission_entry_id` 唯一。
- 售后：`(tenant_id, case_no)` 唯一；
  `(tenant_id, shop_id, status, created_at)` 和会员/订单引用索引。
- 审批：`(tenant_id, business_type, business_id, approval_type, active_flag)` 唯一；
  `(tenant_id, approver_account_id, status, created_at)` 待办索引。
- 通知：`(tenant_id, recipient_account_id, dedup_key)` 唯一；
  `(recipient_account_id, read_at, created_at)` 查询索引。

### 5.3 外键与检查约束

- 金额统一 `DECIMAL`，禁止浮点；提成方向与 `entry_type` 使用检查约束。
- 状态和类型使用检查约束；版本从 0 开始且非负。
- 冲正必须引用同租户原提成且原流水不是冲正流水。
- 结算周期开始时间不得晚于结束时间。
- 审批步骤序号为正；决定状态与决定人/时间必须成组出现。
- 跨模块引用优先保留稳定业务标识与应用层校验；不得通过外键迫使模块直接写入其他模块。

## 6. 状态机

### 6.1 提成规则

`DRAFT -> PUBLISHED -> RETIRED`

- 只有草稿可修改。
- 发布必须有有效生效区间且不能与同优先级同范围规则冲突。
- 已发布规则只能退役，不能回到草稿。

### 6.2 提成流水

`PENDING -> FROZEN -> SETTLED`

附加终态：

- `REVERSED`：原流水已由冲正流水抵销。
- `VOIDED`：仅允许对从未生效的错误草稿结果作废，且必须审计。

冲正流水本身是新 `commission_entry`，不把原流水金额改为零。

### 6.3 结算批次

`DRAFT -> CALCULATED -> CONFIRMED -> PAID -> CLOSED`

- `CALCULATED` 前可删除未确认的草稿明细。
- `CONFIRMED` 后明细不可覆盖，只能取消整批并重新创建。
- `PAID/CLOSED` 后退款差额进入下一批，不重开历史批次。

### 6.4 售后工单

`OPEN -> TRIAGED -> PROCESSING -> WAITING_CUSTOMER -> RESOLVED -> CLOSED`

分支：

- `OPEN/TRIAGED/PROCESSING -> REJECTED`
- `RESOLVED -> REOPENED -> PROCESSING`

每次状态变化必须写工单日志、操作者、原因、版本和审计。

### 6.5 审批实例

`PENDING -> APPROVED | REJECTED | CANCELLED | EXPIRED`

决定为终态；更改决定必须创建新的审批实例并关联原实例。

## 7. 权限与职责分离

计划新增权限：

- `commission:rule:view`
- `commission:rule:manage`
- `commission:entry:view`
- `commission:entry:adjust`
- `commission:freeze`
- `commission:settlement:view`
- `commission:settlement:manage`
- `commission:settlement:approve`
- `aftersale:view`
- `aftersale:create`
- `aftersale:manage`
- `approval:view`
- `approval:decide`
- `notification:view:self`

原则：

- 技师仅以 SELF 查看本人提成和结算，不维护规则、不冻结、不审批。
- 前台可创建售后/退款申请，不能审批本人申请。
- 店长仅处理授权门店；超额度或涉及本人时向上级审批。
- 财务可查看和确认结算，不得改提成规则或护理事实。
- 规则维护者不能单独批准本人发起的追补提成。
- 所有高风险动作同时要求权限、租户/门店范围、版本、幂等和审计。

## 8. 事务、幂等与事件

### 8.1 提成生成

- 事务内锁定/确认来源事实和规则版本。
- 使用 `(tenant, source, staff, entry_type)` 唯一键防止重复入账。
- 保存规则版本和完整计算参数快照。
- 写提成流水、审计与 outbox；任何一步失败整体回滚。

### 8.2 退款联动

- 退款成功后按原提成比例和退款金额计算冲正。
- 未结算提成：追加冲正并更新原流水派生状态。
- 已冻结未结算：追加冲正并保持同一待结算周期可核对。
- 已结算：追加负向冲正，进入下一结算批次。
- 同一退款/原提成组合只能生成一条有效冲正。

### 8.3 售后与审批

- 创建和关键动作要求 `Idempotency-Key` 与稳定请求摘要。
- 售后涉及退款时只调用退款应用服务，不复制退款状态机。
- 审批决定与业务回调采用同事务应用服务或 outbox，消费者必须幂等。
- 通知失败不能回滚已成功业务决定；记录可重试失败状态，不伪造已发送。

## 9. 迁移、兼容、回滚和核对

### 9.1 Expand

1. 新增 M5 表、索引、约束和权限定义。
2. 新权限先定义，再按角色职责显式授权；不使用全角色默认授权。
3. 旧应用忽略新增结构，M5 功能开关默认关闭。
4. 不新增对历史订单、支付、退款、护理事实的强制非空列。

### 9.2 Migrate

- 历史业务不自动生成“已结算提成”，避免伪造员工债权。
- 如需历史模拟，只生成独立、不可入账的重算报告并保存来源时间窗。
- M5 启用水位从明确业务时间开始；水位前事实保持只读。
- 回填按租户/门店/主键分批、可重入并保存批次水位。

### 9.3 兼容

- `/api/v1`、`/api/v2` 保持不变；M5 使用 `/api/v3`。
- `RefundApplicationService` 的成功状态和原有资产冲正语义不变。
- M5 冲正失败时不得把退款回滚为伪失败；使用 outbox 重试和补偿待办，
  并阻止相关提成结算直到一致。
- 管理端采用新路由和权限门禁；前端隐藏不替代后端授权。

### 9.4 回滚

- 关闭 M5 新写入口和消费者，回退应用版本。
- 保留新增表、提成/结算/售后/审批/通知流水和审计。
- 已有业务数据时禁止直接 DROP；通过逻辑停用和后续补偿迁移处理。
- 只有影子库、无业务数据且已验证备份恢复时，才允许单独审批物理回退。

### 9.5 迁移核对

- Flyway `validate` 成功且 checksum 无漂移。
- 迁移前后历史订单、支付、退款、账户、套餐、库存和护理记录行数/汇总不减少。
- 新表租户/门店范围、字符集、时区、外键、检查约束和索引正确。
- 提成净额等于原流水加调整/冲正流水；结算明细可回溯到提成流水。
- 日志、审计和 outbox 不含手机号、健康信息、证件或支付凭据。

## 10. 测试先行清单

### 10.1 规则和提成

1. 同范围同优先级生效区间重叠被拒绝。
2. 已发布规则不可修改，必须新建版本。
3. 同一来源事实重复消费不重复生成提成。
4. 规则选择、计算基数、封顶/保底和金额舍入可确定复现。
5. 跨租户、跨门店和非本人 SELF 查询被拒绝。

### 10.2 冻结、结算和冲正

1. 只有可冻结流水进入冻结，重复冻结幂等。
2. 一个提成流水最多进入一个有效结算批次。
3. 已关闭批次不可修改或重开。
4. 退款对未结算、已冻结和已结算提成分别产生正确冲正。
5. 冲正只追加流水并引用原提成；故障时全部回滚或保留可重试状态。
6. 结算汇总可由明细和提成流水复算。

### 10.3 售后、审批和通知

1. 售后状态非法跳转和过期版本返回稳定冲突。
2. 申请人不能审批本人申请；超额度和跨范围审批被拒绝。
3. 审批决定不可覆盖，更改必须新建实例。
4. 售后触发退款时复用退款应用服务和原幂等机制。
5. 通知同一事件/接收人不重复创建；只允许本人标记已读。
6. 通知通道未配置时返回/记录真实不可用状态，不伪造送达。

### 10.4 数据与边界

1. 模块边界测试禁止交易、护理、售后直接写提成/结算私有表。
2. 真实 MySQL 8 验证唯一键、检查约束、锁和事务回滚。
3. 日志扫描验证敏感数据不泄露。
4. API 契约、权限映射、管理端路由和后端路由一致。
