# FACE 商用新系统升级可行性评估 V1.0

> 评估对象：现有 `E:\face` 系统与四份《美容院店铺管理系统商用设计文档 V1.0》  
> 评估日期：2026-07-26  
> 结论级别：架构、数据库、API、产品范围与实施可行性预评估  
> 评估方式：数据库架构、API/系统架构、产品/交付三个专项小组并行审阅，主线程完成文档解析、WPS 逐页核查、代码索引工具 代码审阅与构建验证

## 1. 最终结论

### 1.1 决策

**Conditional Go：可以基于现有系统完成新系统升级，但必须定义为“渐进式 V3 商用平台演进”，不能定义为普通功能迭代。**

建议批准：

- 继续以 `backend-next + admin-next + front-next` 为工程底座；
- 保留模块化单体和单库事务能力；
- 按领域扩展新表、新用例和商业 API 适配层；
- 先完成单店、单一真实营业纵切，再逐步引入套餐、支付、提成和售后；
- 采用扩展—迁移—切换—收缩的兼容迁移方式。

不建议批准：

- 按新 PRD 当前“大而全 P0”一次性全面开工；
- 原地用新 `/api/v1` 覆盖 legacy `/api/v1` 或现有 `/api/v2`；
- 直接重命名现有 `shop/member/staff/service_record` 等核心表；
- 在权限、幂等、对账、测试和恢复体系未补齐前商用上线；
- 立即拆分微服务。

### 1.2 一句话判断

现有系统不是废弃原型：它已经具备租户门店、会员、预约、服务、交易、库存和审计的关键事务主干；但距离四份文档定义的完整多门店商业 ERP 平台仍有明显距离，当前更接近**可复用的约三成工程底座**，而不是接近完成的商用系统。

## 3. 定量差距

### 3.1 数据库

- 新数据库设计：约 110 张核心表。
- 现有美容基础库叠加 V2 Flyway：约 44 张规范化表。
- 同名表约 12 张。
- 现有系统已有关键业务脊柱，但套餐、提成、采购、资源、审批、Outbox 等仍是大规模新增领域。

新文档目前是逻辑模型，不是可直接执行的完整 DDL：

- 110 张表只详细展开约 17 张；
- 多数表缺完整字段、外键、唯一作用域和删除策略；
- Outbox、资源锁、分区和回滚方案尚未物理化；
- `sale_order_id` 与 `sales_order` 等命名存在不一致。

### 3.2 API

商用接口清单共 156 个接口。

| 类型 | 数量 | 比例 |
|---|---:|---:|
| 已有完整对应能力 | 22 | 约 14% |
| 可通过适配或扩展复用 | 27 | 约 17% |
| 需要新建或重大改造 | 107 | 约 69% |

现有路由：

- `backend-next`：54 个 `/api/v2` 路由；
- legacy `backend`：31 个已占用的 `/api/v1` 路由；
- 商用文档又将 Base URL 定义为 `/api/v1`。

因此不能简单计算为“54/156 已完成 35%”。现有路由包含重复客户端入口和聚合资源接口，按业务意图映射后的完整覆盖约 14%，含部分覆盖约 31%。

## 5. 最值得保留的现有能力

### 5.1 模块化单体与技术栈

现有 Java 21、Spring Boot、MySQL 8、Flyway、Vue 3 技术组合与新文档推荐方向基本一致。无需为了文档写的是 Spring Boot 3 而主动降级现有 Spring Boot 4.1；应以依赖兼容性和测试结果决定。

### 5.2 租户与门店主干

`TenantPrincipal` 已携带租户、区域、门店范围，主要业务表已有 `tenant_id/shop_id`。这一层可作为商用多门店升级的基础。

### 5.3 预约一致性

现有预约创建会校验：

- 会员；
- 项目；
- 技师；
- 技能；
- 排班；
- 时间重叠。

预约改期和状态变化已有版本控制和历史记录。房间、床位和仪器资源尚未覆盖，但无需重写已有技师预约逻辑。

### 5.4 服务完成事务

现有服务完成能够在同一事务中处理：

- 护理档案；
- 服务耗材；
- 库存流水和余额；
- 服务记录；
- 预约状态。

这是整个升级中复用价值最高的事实底座。

### 5.5 交易与库存账本

现有系统已有：

- 订单；
- 支付/退款记录；
- 会员账户账本；
- 库存余额和不可变流水；
- 调拨及审批；
- 部分业务幂等键。

它们可以扩展为商用资金和资产模型，无需从零开始。

## 6. 上线阻断项

### 6.1 权限与 SELF 范围

当前权限校验可能将“门店 A 的权限”与“门店 B 的访问范围”组合使用；`BEAUTICIAN` 虽被定义为 SELF scope，但预约、服务和会员查询并未始终追加当前技师 `staff_id` 条件。

风险：

- 技师可能读取同店其他技师的预约；
- 技师可能读取同店其他客户和护理记录；
- 健康、过敏和护理数据存在严重隐私风险。

必须统一为：

```text
authorize(
  principal,
  permissionCode,
  ResourceScope(tenantId, regionId, shopId, ownerId)
)
```

权限、数据范围和资源所有者必须在同一条授权决策中完成。

### 6.2 技师直接完成旁路

现有技师客户端可通过通用预约状态接口把 `IN_SERVICE` 更新为 `COMPLETED`，绕过完整服务完成事务，可能产生：

- 预约已完成；
- 护理档案待补；
- 耗材未扣；
- 库存无流水；
- 后续仍可结算。

必须取消技师直接提交预约完成的能力，统一走服务完成命令。

### 6.3 API 版本冲突

不能将商用文档中的 `/api/v1` 直接用于当前应用：

- legacy 已使用 `/api/v1`；
- next 前端已绑定 `/api/v2`；
- 商用契约的路径、字段和响应均不同。

推荐：

- 内部使用 `/api/v3`；或
- 使用独立 context root `/face-commercial/api/v1`；或
- 新网关域名对外暴露 `/api/v1`。

现有 `/api/v1` 和 `/api/v2` 在迁移期保持兼容。

### 6.4 契约不一致

新文档与当前实现存在以下差异：

| 领域 | 商用文档 | 当前实现 |
|---|---|---|
| 响应 | 字符串业务码、`request_id`、时间戳 | HTTP 数字 code + 中文消息 |
| 分页 | `items/page_size` | `records/pageSize` |
| 金额 | JSON 字符串 | JSON number |
| 时间 | 带时区 ISO-8601 | 多处 `LocalDateTime` |
| 幂等 | `Idempotency-Key` Header | 多处放在 Body，策略不统一 |
| 错误 | 稳定业务错误码 | 多数依赖中文异常消息 |

商业 API 适配层必须统一这些契约，不能直接让新客户端依赖旧 DTO。

### 6.5 身份与会话不足

当前身份系统主要满足简单 token 登录，缺少：

- refresh token；
- 设备会话；
- 单设备注销；
- 全局撤销；
- 验证码和登录限流；
- 离职账号会话即时失效。

这些是商用安全基线，不应延后到上线后补。

### 6.6 幂等和请求指纹

现有支付、退款、库存和服务完成已有部分幂等基础，但：

- 预约创建和订单创建缺统一幂等；
- Header/Body 规则不一致；
- `idempotency_record` 尚未形成通用服务；
- 同一 key 不同金额或负载可能返回旧结果；
- 并发重复请求缺统一重放响应。

必须保存请求摘要：

```text
tenant + operation + idempotency_key + request_fingerprint
```

同键同负载返回原结果；同键不同负载返回明确冲突。

### 6.7 Outbox 和异步可靠性缺失

新文档要求服务完成、支付、退款、库存、提成、回访等跨域事件，但现有源码没有完整 Outbox/Inbox、发布器或消费者。

在引入套餐、提成、通知和报表前，应先建设：

- `outbox_event`；
- 消费去重；
- 重试和死信；
- 事件查询与重放；
- 业务对账。

### 6.8 测试与运维不足

现有 9 个通过测试只覆盖少量状态和权限策略，缺少：

- 跨租户、跨门店、跨技师越权；
- 预约并发；
- 事务回滚；
- 支付回调重放；
- 库存原子性；
- 退款并发；
- API 契约；
- 前端端到端；
- 恢复演练。

现有构建成功证明代码可继续演进，不代表已满足商用质量门槛。

## 7. 四份文档内部需要先解决的冲突

### 7.1 P0 范围过大

新 PRD 将以下能力全部列入 P0：

- 组织权限；
- 客户；
- 预约和服务；
- 套餐、储值和积分；
- 真实支付和退款；
- 采购库存；
- 提成；
- 售后；
- 报表；
- 审计；
- 三端完整闭环。

这与当前 `PRODUCT.md` 将套餐/次卡、复杂积分、自动提成和支付集成列为非目标相冲突，也与技师端 V1.1 的范围收敛结论相冲突。

### 7.2 状态机混合

PRD 把预约、服务、客户确认、结算、退款和售后放在同一状态轴上。

建议坚持独立聚合：

```text
Appointment
ServiceOrder / ServiceRecord
Confirmation
SalesOrder / Payment
Refund
Exception / AfterSales
```

每个聚合有自己的状态、版本、权限和冲正规则。

### 7.3 客户确认语义冲突

新 PRD 要求客户确认后才正式完成服务和核销；现有服务中心与技师端 V1.1 认为真实服务和耗材事实应先落账，客户确认是独立证据。

推荐：

- 服务事实和服务耗材先完成；
- `confirmation=PENDING`；
- 客户确认、提出争议，或经理带理由豁免；
- 后续结算、提成资格或争议流程根据确认状态处理。

客户确认不应阻止真实服务事实落账。

### 7.4 阶段依赖倒置

实施文档阶段 3 要求完成服务和客户确认，阶段 4 才建设交易、套餐和库存；但服务开始与完成又要求校验支付、套餐和耗材库存。

按原顺序开发会迫使团队使用假数据或临时旁路。

推荐先完成一条最小营业纵切，再扩展资产和资金能力。

### 7.5 自动派单优先级冲突

管理端和阶段 3 将自动派单列为早期能力，但版本规划又把规则派单放在 P2。

P0 仅保留：

- 人工派单；
- 确定性资格筛选；
- 可解释的候选技师排序。

规则派单留到 P2。

## 8. 推荐目标架构

### 8.1 总体形态

继续采用模块化单体：

```text
legacy /api/v1 ─┐
current /api/v2 ├─→ API Adapters
commercial API ─┘
                    ↓
              Application Use Cases
                    ↓
               Domain Policies
                    ↓
       JDBC Adapters + Local Transactions
                    ↓
               MySQL + Outbox
```

现有大型 `JdbcTemplate` Service 可暂时作为适配器保留；新功能逐步拆成应用用例和领域策略，不做一次性重写。

### 8.2 领域边界

- Identity & Organization
- Customer
- Catalog & Pricing
- Appointment & Resource
- Service Order & Care
- Package / Wallet / Loyalty
- Commerce / Payment / Refund / Cashier
- Inventory / Procurement / Device
- Performance / Commission / Reporting
- After-sales / Approval / Notification / Audit

### 8.3 前端

- `admin-next`：继续作为总部和门店管理端迁移壳。
- `front-next`：继续承载客户和技师角色，但按角色提供独立信息架构。
- 技师 P0：先完成本人日程和服务闭环。
- 客户端小程序/App：待商业纵切稳定后，再评估 uni-app/Taro 独立工程。

## 9. 数据库升级策略

### 9.1 不原地重命名

迁移期保留：

- `shop`，不直接改为 `store`；
- `member`，不直接改为 `customer`；
- `staff`，不直接改为 `employee`；
- 当前 `/api/v2` DTO 和查询。

通过商业 API 适配器完成外部命名转换。

### 9.2 扩展—迁移—切换—收缩

1. 扩展新表和可空字段；
2. 分批回填历史数据；
3. 双写并进行影子读核对；
4. 按租户和领域灰度切换；
5. 旧表转只读；
6. 保留完整回滚窗口；
7. 最后清理兼容字段。

### 9.3 最大迁移难点

1. 当前 `service_record` 实际更接近新 `service_order`，需进行语义迁移。
2. 会员手机号目前需要标准化、跨店去重、加密和哈希检索。
3. 支付和退款需要拆分申请、支付单、交易和执行。
4. 库存需要补批次、供应商和单据链。
5. 展示型 `care_package` 不能自动等同于真实套餐权益。
6. 提成没有可靠历史源，需要业务确认期初。
7. 部分 Flyway 脚本写死 `tenant_id=1/shop_id=1`，不能直接用于多租户商用迁移。
8. 时间、金额和库存精度需统一。

### 9.4 必做数据对账

- 会员跨店重复与手机号规范；
- 订单、支付和退款汇总；
- 会员账户余额与最后账本；
- 库存余额与流水；
- 预约时间和终态；
- 一预约多服务单；
- 一服务单多订单；
- 空幂等键和重复业务号；
- 跨租户/跨门店外键错链；
- 历史时间时区转换。

## 10. 推荐实施路线

### M0：基线冻结与可行性补全，2 周

- 完成真实角色访谈和现状指标；
- 冻结 P0 与“不做清单”；
- 修正文档状态机和阶段依赖；
- 输出 110 表完整物理 DDL；
- 建立需求—接口—表—测试追踪矩阵；
- 明确 API 版本策略；
- 确定 RPO/RTO、灰度周期和对账容差。

退出门槛：业务、产品、技术、测试和门店共同签字。

### M1：安全与工程底座，2–4 周

- 修复 SELF/SHOP/REGION 授权；
- 阻断技师直接完成旁路；
- 会话撤销、refresh、logout 和设备会话；
- request ID、业务错误码和契约适配；
- 通用幂等服务与请求指纹；
- CI/CD、凭据治理和自动化测试底座；
- 数据质量基线和恢复演练。

退出门槛：越权、重复写入和旁路均被自动化测试阻断。

### M2：主数据与资源，3–5 周

- 客户敏感信息和风险；
- 项目流程和资格；
- 房间、床位、仪器和资源占用；
- 排班、人工派单和确定性推荐；
- 迁移兼容映射。

退出门槛：真实门店基础数据可导入，资源并发只有一笔成功。

### M3：最小营业纵切，4–6 周

完成：

```text
客户
→ 预约
→ 签到
→ 技师开始服务
→ 护理与耗材
→ 库存
→ 单一支付方式
→ 唯一订单
→ 日终对账
```

退出门槛：单店可连续完成真实模拟营业日，所有事实可追溯且对账为零差异。

### M4：资产与资金增强，6–10 周

- 套餐、储值和积分账本；
- 支付回调和组合支付；
- 退款申请、审批和执行；
- 收银交班和对账；
- 采购、批次、效期和盘点；
- Outbox/Inbox 和事件重放。

退出门槛：重复回调 10 次只入账一次，权益和库存不重复扣减。

### M5：提成、售后与报表，6–8 周

- 提成规则版本和多人拆分；
- 结算、申诉和退款冲减；
- 回访、评价、投诉和证据锁定；
- 审批和通知；
- 基础经营、库存和财务报表。

退出门槛：所有计算可追溯到订单、规则版本和原始事件。

### M6：商用门禁，4–6 周

- 全量回归、接口、并发、安全和端到端测试；
- 数据迁移演练；
- 压测；
- 备份、恢复和回滚；
- 预发布 UAT；
- 1 家门店封闭试点；
- 分批放量。

## 11. 工期与资源判断

以下为早期 ROM，不是正式报价；置信度约 60%，误差约 ±35%。

| 范围 | 预计工期 | 预计投入 |
|---|---:|---:|
| 仅技师端单店闭环 | 5–6 周 | 小型产品/研发/QA 组合 |
| 收窄后的商用单店纵切 | 12–16 周 | 20–30 人月 |
| 新 PRD 原始 P0 全部实现 | 7–10 个月 | 65–100 人月 |

原始 P0 需要产品/业务、UX、后端、管理端、客户端/移动端、QA、DevOps/安全共同投入。支付、短信/消息、对象存储、合规、安全测评和数据迁移可能产生独立采购与排期。

## 12. 试点与放量门槛

首批建议：

- 1 家门店；
- 5–10 名技师；
- 低风险项目；
- 至少连续 10 个营业日；
- 覆盖一次退款、一次交班和一次库存盘点。

放量前必须满足：

- 服务闭环率 ≥ 90%，稳定期目标 ≥ 95%；
- 越权成功数为 0；
- 重复订单、扣款、核销和扣库为 0；
- 负库存为 0；
- 支付、套餐、库存和订单日终对账差异为 0；
- 无 P0/P1 数据一致性或安全缺陷；
- 预约冲突校验 P95 ≤ 1 秒；
- 常用列表 P95 ≤ 1.5 秒；
- 备份恢复和回滚演练通过；
- 20% → 50% → 100% 放量，每档至少观察 3 个完整营业日。

任一核心门槛失败，应暂停扩量。

## 13. Go / No-Go 门禁

### 可以进入升级开发

- 业务接受缩减后的 P0；
- 明确商业 API 独立版本；
- 批准渐进式数据库迁移；
- 先修权限和服务完成旁路；
- 配置真实试点门店和负责人；
- 同意先做纵切、后做完整 ERP。

### 不允许商用上线

以下任一项未完成时维持 No-Go：

1. SELF/SHOP/REGION 权限范围仍可能组合越权；
2. 技师仍可绕过服务事务直接完成；
3. API 版本会覆盖 legacy 或 next 客户端；
4. 预约、订单、支付、退款和库存没有统一幂等与请求指纹；
5. 外部支付没有验签、退款执行和对账；
6. 没有 Outbox/Inbox 和事件重放；
7. 套餐、采购、提成等已承诺域仍无可靠账本；
8. 缺少跨租户、并发、回滚和契约测试；
9. 未完成恢复演练和迁移对账；
10. 未经过单店连续营业试点。

## 14. 建议立即执行的两周任务

1. 将四份商用文档和现有 `PRODUCT.md` 合并为一份范围基线。
2. 将新 PRD P0 重写为“最小真实营业纵切”。
3. 修复技师 SELF 范围和直接完成旁路。
4. 确认商业 API 使用 `/api/v3` 或独立 context root。
5. 建立 156 个接口的映射清单：已有、适配、新建、取消。
6. 补齐 110 张表的物理 DDL 和旧表映射。
7. 建立数据质量扫描和余额对账报告。
8. 为预约并发、服务完成、支付重放、退款和越权补集成测试。
9. 建立需求—角色—接口—表—测试—负责人追踪矩阵。
10. 用 1 家真实门店验证必填字段、支付方式和异常流程。

## 15. 最终建议

批准项目时，项目名称建议从“现有系统功能升级”改为：

> FACE V3 商用平台渐进式升级与单店试点

第一阶段目标不是实现文档中的所有菜单，而是：

> 在不破坏现有 V2 的前提下，形成一条安全、可追溯、可对账、可恢复的真实营业闭环。

做到这一点后，再按套餐、支付、采购、提成和售后逐域扩展。基于现有系统演进比全部重写更合理，也能保留已有预约、服务完成、交易和库存的一致性价值；但只有严格执行兼容迁移、范围收敛和商用门禁，升级方案才具备可控风险。
