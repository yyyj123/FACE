## 1. 决策结论与范围冻结

### 1.1 最终产品形态

一期只交付两个可见产品：

```text
FACE 用户端
└─ 响应式 H5/Web：手机浏览器、微信内置浏览器、电脑浏览器

FACE 运营管理平台
└─ 响应式 Web：电脑完整管理，手机提供高频管理能力
```

后端继续使用现有模块化单体和 MySQL/Flyway。技师仍作为“可预约服务资源”存在，但不提供独立技师端和技师登录账号。

二期开发微信小程序，复用一期后端的用户、项目、技师排班、预约、卡项、订单、积分、商城、评价、售后和通知能力，不再复制一套业务规则。

### 1.2 方案一的实施原则

1. 保留现有 `backend-next`、`admin-next`、`front-next` 和数据库主线。
2. 不删除已存在的技师端、库存、采购、提成、培训、多门店等旧能力；本期仅冻结、隐藏入口和停止新增。
3. 不修改已执行 Flyway 迁移，不覆盖资金、积分、卡项、库存、退款、通知等历史事实。
4. 新功能优先复用现有会员、预约、订单、套餐、售后、营销、通知和审计模块；确有边界冲突时先写架构决策记录。
5. 用户端、运营平台和未来微信小程序只负责交互，价格、空闲时段、优惠、积分、权益和退款结果均由后端计算。
6. 当前按单店上线，所有核心表、接口和权限继续保留 `tenant_id`、`shop_id` 等多门店扩展边界。

### 1.3 本期明确不做

- 不交付独立技师端。
- 不交付总部、区域、分店多层后台菜单体系。
- 不交付前台、客服、售后、财务、仓库、区域经理等复杂岗位角色。
- 不交付采购、供应商、仓库调拨、复杂盘点、提成结算和员工培训。
- 不在一期直接接入真实微信支付、支付宝或银行卡聚合服务商；只完成统一支付框架、运营配置入口和 DEMO 模拟支付。
- 不把未知支付服务商仅通过填写 URL 和密钥自动接入；具体服务商仍需开发适配器。
- 不在一期实现物流轨迹聚合查询；管理员手工填写物流公司和运单号。
- 不允许后台执行任意 SQL、脚本或自定义计算公式。
- 不在一期实现 Kubernetes、微服务拆分或服务网格。

## 2. 当前基线与 B0 状态

当前系统已具备会员、预约、订单、套餐、退款、售后、营销、通知、权限、审计等基础能力。V3.0 不重新实现这些领域，而是先验证真实代码和数据库结构，再决定复用、扩展或冻结。

B0 当前标记为“有条件未通过”：

- 原始交付目录没有 Git 历史，无法提供真实升级前 commit/tag；
- 现有 Docker 运行脚本写死旧 Flyway 版本 `2026080103`；
- 默认宿主机端口 `8290` 被占用；
- 使用独立端口的等价验证已经完整通过。

正式功能开发前必须完成 B0-R：

1. 建立明确标注“首次可追溯快照、非原始历史”的 Git 基线。
2. 验收脚本使用 Flyway `migrate + validate + flyway_schema_history` 动态判断，不再写死版本。
3. 宿主机端口参数化并增加启动前占用检查。
4. 使用官方脚本从干净状态重复完成构建、迁移、健康检查和重启验证。
5. 在 `docs/verification/B0/` 留存命令、版本、结果和来源限制。

B0-R 未通过前，项目组 不得进入业务阶段。

### 3.1 环境入口

| 环境 | 入口 | 说明 |
| --- | --- | --- |
| dev/test | 本地端口 | 开发与自动化测试 |
| demo | `/` 演示门禁，`/admin/`、`/client/`、`/api/` | Windows 11 + Docker Desktop + Cloudflare Quick Tunnel |
| staging | 固定测试域名 | 使用测试商户或禁用真实支付 |

### 3.2 单店上线与多店扩展

一期使用：

```text
BUSINESS_MODE=SINGLE_SHOP
DEFAULT_SHOP_ID=<配置值>
```

约束：

- 用户端不显示门店选择，后端解析默认门店。
- 前端禁止写死 `shopId=1`。
- 默认门店不存在、停用或不属于当前租户时，拒绝预约和下单。
- 用户账号属于租户/品牌；预约、订单、技师排班、评价和商城自提属于门店。
- 卡项提前支持 `ALL_SHOPS` 与 `SPECIFIED_SHOPS` 适用范围。
- 后续切换 `MULTI_SHOP` 时仅增加门店选择和权限范围，不重写核心数据。

## 4. 用户与权限模型

### 4.1 用户端身份

| 身份 | 能力 |
| --- | --- |
| 游客 | 浏览首页、活动、护理项目、在售卡项、技师公开资料、商城商品、门店介绍和规则 |
| 会员用户 | 查看技师具体排班、预约、下单、购买卡项、领取优惠券、使用积分、评价、售后、查看个人资产 |

正式用户端支持：

- 手机号 + 短信验证码注册/登录；
- 手机号 + 密码登录；
- 验证码找回密码；
- 同一手机号在同一租户下只对应一个会员；
- 老客户通过手机号匹配历史会员和卡项，不能生成重复空账号。

DEMO 环境固定验证码为 `888888`，页面明确提示“演示验证码，未发送真实短信”；生产环境严禁自动降级到固定验证码。

### 4.2 管理平台角色

只保留两个角色：

```text
SUPER_ADMIN  超级管理员
ADMIN        普通管理员
```

普通管理员负责用户端的日常运营：内容、项目、技师、排班、预约、订单、卡项、积分、商城、发货、评价、售后和导入预检。

超级管理员额外负责：

- 管理员账号创建、停用和重置；
- 支付、短信、微信、物流适配器及密钥配置；
- 全局积分参数和风险阈值；
- 正式数据导入；
- 批量作废优惠券和自动补发；
- 超阈值资金、权益、积分与库存操作；
- 审计、安全和生产级系统配置。

### 4.3 风险阈值

普通管理员默认上限：

| 操作 | 默认上限 |
| --- | ---: |
| 单笔退款 | 500 元 |
| 单次积分调整 | 2000 积分 |
| 单次储值调整 | 500 元 |
| 单项卡次返还 | 2 次 |
| 单个 SKU 库存调整 | 20 件 |
| 单用户单次补偿券 | 2 张 |
| 批量资产操作 | 禁止 |

超过阈值时普通管理员只能提交处理申请，由超级管理员执行。系统按同一用户、订单、售后工单和时间窗口累计判断，禁止通过拆分操作绕过上限。

## 6. 内容、护理项目与技师资源

### 6.1 首页与内容配置

管理平台可配置：轮播图、推荐护理、推荐卡项、活动专区、积分商城专区、公告、门店介绍、联系方式、展示顺序、草稿、定时发布和下线。

内容状态：

```text
DRAFT → SCHEDULED → PUBLISHED → OFFLINE
```

已发布内容修改后不得静默改变历史订单或预约规则。

### 6.2 护理项目

每个护理项目配置：

- 名称、分类、图片、详情、原价和在售状态；
- 服务时长；
- 预约开始时间间隔；
- 服务前缓冲、服务后缓冲；
- 最短提前预约时间；
- 是否允许当天预约；
- 免费取消时限、最晚改期时限、允许改期次数；
- 逾期取消违约类型及参数；
- 可服务技师；
- 是否允许卡项、优惠券、折扣卡或积分抵扣；
- 是否产生积分及积分倍率覆盖规则。

时间间隔由项目独立配置，例如 15/20/30/60 分钟。后端根据服务时长、前后缓冲、排班和冲突计算可选开始时间，前端不得自行生成。

### 6.3 技师资源

技师是品牌级基础档案与门店任职关系的组合，至少包含：

- 展示名称、头像、简介、擅长项目；
- 可服务护理项目；
- 当前门店任职状态；
- 固定班次、临时排班、休息、请假、停约；
- 公开评分和审核通过的公开评价。

一期不创建技师登录账号。管理平台维护其资料和日程。

用户只能看到技师是否可预约，不得看到其他顾客姓名、手机号、项目、订单或卡项信息。

## 7. 预约、时间锁与候补

### 7.1 日期与时段

- 页面每次展示连续 7 天，可前后翻页；
- 最多预约未来 30 天；
- 每次只请求当前 7 天；
- 提交时间锁、下单和支付确认前均重新校验；
- 最短提前预约时间按项目配置；
- 管理员代客预约可以突破最短提前时间，但必须填写原因；
- 任何角色均不得突破时间冲突。

可预约区间计算：

```text
技师排班
- 休息/请假/停约
- 已确认预约
- 待支付时间锁
- 服务前缓冲
- 服务时长
- 服务后缓冲
= 可预约开始时间
```

### 7.2 指定与不指定技师

用户可以：

1. 指定技师，查看该技师未来 30 天日程；
2. 选择“不指定技师”，系统按低负载优先 + 同负载轮询匹配。

负载按当天已确认预约、待支付锁和缓冲占用分钟数计算，不按订单数量计算。

系统在支付前展示匹配技师，用户可以接受、重新匹配或改为手动选择。重新匹配时先锁定新技师，再释放旧锁，避免失去原时间。

### 7.3 单次护理购买与预约

```text
选择项目
→ 选择/匹配技师
→ 选择时间
→ 查看并确认本次取消、改期、违约条款
→ 创建订单并锁定完整占用区间
→ 支付成功或零元订单成立
→ 自动确认预约
```

支付超时、订单关闭或权益校验失败后释放完整时间锁。

### 7.4 预约条款

每次预约都必须重新勾选确认。用户端至少在项目详情、时间确认页和订单确认页展示：

- 免费取消截止时间；
- 最晚改期时间；
- 允许改期次数；
- 逾期处理方式；
- 固定扣款、比例扣款、扣卡次或不可退款等具体结果。

后端保存条款版本、规则快照、用户确认时间和本次截止时间。项目规则后续变更不影响既有预约。

违约类型：

```text
FULL_REFUND
FIXED_FEE
PERCENTAGE_FEE
DEDUCT_CARD_TIMES
NON_REFUNDABLE
```

### 7.5 候补名单

顾客可为已约满技师提交候补：项目、技师、可接受日期、时间范围、浮动范围、最晚通知时间及是否接受其他技师。

状态：

```text
WAITING → MATCHED → WAITING_CONFIRMATION → CONFIRMED
                           ├→ EXPIRED
                           ├→ CANCELLED
                           └→ INVALID
```

空位出现后：

- 按加入时间和匹配度依次处理；
- 同一空位一次只通知一位顾客；
- 锁定 15 分钟；
- 使用站内高优先级提醒；
- 顾客必须重新确认预约条款并支付或冻结卡项权益；
- 超时释放并通知下一位；
- 不自动创建预约。

## 8. 订单、支付与优惠决策

### 8.1 支付架构

一期完成统一支付中心和适配器接口：

```text
PaymentChannelAdapter
├─ DEMO_MOCK       一期实现
├─ WECHAT          预留
├─ ALIPAY          预留
└─ AGGREGATOR      具体服务商确定后开发
```

统一能力包括：支付单、状态机、幂等、支付超时、回调防重复、退款单、对账任务框架、审计和运营配置页。

生产环境未配置真实渠道时保留支付按钮并提示“支付渠道暂未开通”，不得自动降级为模拟支付。

### 8.2 优惠四选一

普通护理和卡项订单的优惠方式：

```text
活动价 / 优惠券 / 折扣卡 / 积分抵扣 / 不使用优惠
```

其中活动价、优惠券、折扣卡、积分抵扣互斥。系统展示全部可用方案及最终金额，由用户主动选择；默认不使用优惠，可标记“优惠最多”但不得自动勾选。

付款方式：

- 一张储值卡；或
- 一个在线支付渠道。

不支持两张储值卡、储值卡余额不足后补在线支付、多个在线渠道拆分支付。

### 8.3 零元订单

应付金额为 0 时生成 `ZERO_AMOUNT` 支付记录，不调用外部支付渠道。零元订单仍必须创建订单、预约、优惠/权益流水和幂等记录。

取消时按预约条款返还或扣除优惠券、体验券和其他权益，不产生资金退款。

## 9. 三类卡项

一张卡只属于一种类型：

```text
COMBO_TIMES   次数组合卡
STORED_VALUE  储值卡
DISCOUNT      折扣卡
```

### 9.1 次数组合卡

一张卡可包含多个护理项目，各自配置总次数、不限次、适用门店、有效期和使用规则。

预约成功冻结 1 次，服务完成确认后正式核销；正常取消释放，逾期取消按条款扣除或返还。

### 9.2 储值卡

分别记录本金、赠送金、冻结金额、消费、退款和到期失效。扣款顺序由管理平台配置，退款按原扣款构成返还。

不得只保存一个可覆盖总余额；必须使用资产批次和不可删除流水。

### 9.3 折扣卡

配置适用项目/分类、折扣比例、最低消费、最高优惠、使用次数、有效期和排除项目。折扣卡只计算优惠，折后金额仍使用一张储值卡或一个在线渠道支付。

### 9.4 卡项来源

```text
ONLINE_PURCHASE
OFFLINE_SALE
GIFT
REISSUE
LEGACY_IMPORT
```

用户端可在线购买；管理端可录入线下销售、赠送、补发和历史导入。各来源必须在报表和审计中区分。

## 10. 护理优惠券与活动

一期支持：

```text
THRESHOLD_REDUCTION  满减券
CASH                 无门槛现金券
DISCOUNT             折扣券
SERVICE_EXPERIENCE   指定护理体验券
```

来源：管理端定向发放、用户活动领取、售后补偿发放。

状态：

```text
UNCLAIMED → AVAILABLE → LOCKED → USED
                       ├→ EXPIRED
                       └→ CANCELLED
```

每张券可配置“整单退款返还或不返还”，部分退款默认不返还。退款真正成功后才返券。

体验券冻结后创建零元预约，护理完成后核销；逾期取消按条款处理。

## 11. 履约、顾客确认与评价

### 11.1 履约状态

```text
CONFIRMED
→ ARRIVED
→ IN_SERVICE
→ PENDING_CUSTOMER_CONFIRMATION
   ├→ COMPLETED
   └→ AFTER_SALES_PROCESSING
```

管理平台更新“已到店、服务中、结束护理”。结束护理后不立即核销，用户端收到完成确认请求。

顾客 24 小时内：

- 确认完成：正式核销卡项/储值/体验券并开放评价；
- 提出异议：进入售后，停止自动完成；
- 未操作：系统自动完成并记录 `SYSTEM_AUTO_CONFIRMED`。

### 11.2 评价

三个必填评分：技师服务、护理项目效果、门店环境。综合评分由后端计算三项算术平均值，保留 1 位小数。

顾客选择：公开展示或仅门店可见。公开评价进入审核，管理员只能审核、回复、隐藏，不得修改顾客原文和评分。

顾客可以随时修改或删除当前评价：

- 每次修改形成版本；
- 已公开评价修改后立即隐藏，新版本重新审核；
- 删除为逻辑删除，不删除历史版本和售后记录；
- 已删除评价不参与当前公开评分。

任一分项或综合评分低于 3 星，或顾客主动要求联系时，自动创建/关联售后工单。

## 12. 售后

顾客在服务最终完成后 7 天内发起售后；超期后普通入口关闭，超级管理员可基于特殊原因人工创建并留审计。

处理方案：

```text
REFUND
REDO_SERVICE
RESTORE_ENTITLEMENT
COMPENSATION_COUPON
REJECT
```

具备权限且未超过风险阈值的普通管理员可直接处理；超过阈值由超级管理员执行。所有操作关联有效售后工单、原因、凭证、幂等键和不可删除流水。

管理员提交处理结果后：

- 顾客有 48 小时确认；
- 未操作自动结案；
- 原售后有效期内允许重新申诉一次；
- 退款渠道仍处理中时不得提前进入等待顾客确认。

历史卡不支持用户端直接线上退款，只能提交售后，由管理员核实后线下处理并登记资金和权益结果。

## 13. 积分账户、任务与抵扣

### 13.1 积分账户

采用批次 + 流水：

- 可用积分、冻结积分、累计获得、累计消耗；
- 获得时间、到期时间、剩余量、来源规则和业务对象；
- 最早到期积分优先消耗；
- 不允许直接覆盖余额。

默认有效期为获得后 12 个月。超级管理员可设置 1-60 个月全局有效期，修改只影响新积分批次。

到期前 30 天、7 天、1 天发送站内汇总提醒。

### 13.2 积分获得

全局基础比例由管理平台设置，并允许项目、卡项和活动覆盖：

```text
指定活动规则
→ 指定项目/卡项规则
→ 全局基础规则
```

积分按实际支付金额计算，最终结果四舍五入取整。每条规则可配置单笔上限和用户活动期上限。

到账节点：

- 护理项目：服务最终完成；
- 卡项购买：支付成功且权益到账；
- 积分商城实物兑换：不再产生消费积分；
- 商城人民币或组合订单：确认收货后，可按人民币实付部分发放；
- 退款：按原发放记录扣回。

### 13.3 积分任务

支持：注册、完善资料、每日签到、完成护理、有效评价、活动任务和管理员补偿。

每日签到使用连续阶梯：周期天数、每日奖励、周期奖励、是否循环、活动期上限均由管理端设置；中断后从第 1 天重新计算。点击签到成功后立即自动到账。

### 13.4 普通订单积分抵扣

管理端按项目或卡项配置：兑换比例、最低使用积分、使用步长、单笔抵扣比例、最高金额、每日上限和时间范围。

积分抵扣属于优惠方式，与活动价、优惠券和折扣卡四选一。抵扣后剩余金额使用一张储值卡或一个在线渠道支付。

## 14. 积分商城与实物商城

### 14.1 商城范围

商城既支持积分兑换，也支持人民币购买和固定“积分 + 人民币”组合支付。

商品可为：实物产品或护理兑换权益。

管理端可配置：商城首页、分类、商品、SKU、三种购买模式、库存、运费、自提、配送、活动、商城优惠券、订单、发货、退换货和统计。

### 14.2 商品与 SKU

商品主信息：名称、分类、品牌、图片、详情、配送、自提、运费、售后、发布状态。

每个商品可有多个 SKU，每个 SKU 独立配置：

- 规格组合、SKU 编码、图片和重量；
- 人民币售价；
- 纯积分价格；
- 唯一一个固定“积分 + 人民币”档位；
- 三种购买模式启停；
- 可售、冻结、已售、退回待检、报损库存；
- 每人限购和活动库存。

三种模式共用同一 SKU 库存。

### 14.3 商品发布

```text
DRAFT
→ SCHEDULED
→ ON_SALE
→ SCHEDULED_OFFLINE
→ OFFLINE
```

库存为 0 显示 `SOLD_OUT`；停用使用 `DISABLED`。支持草稿、立即上架、定时上架、定时下架和手动下架。

### 14.4 购物车、拆单与合包

购物车支持多商品、多 SKU。加入购物车不冻结库存，提交结算时重新校验。

不同购买方式在结算时拆为子订单：

```text
商城母订单
├─ 纯人民币子订单
├─ 纯积分子订单
└─ 积分+人民币子订单
```

还需按配送方式、自提门店、单独发货和运费模板兼容性拆分。

相同地址、相同配送方式、运费模板兼容、无单独发货限制且人民币款项均成功的子订单可合并为一个包裹和运单号。包裹与订单分离建模，支持一单多包、一包多子单。

### 14.5 商城优惠

纯人民币模式可使用：商品活动价或一张商品优惠券，二者互斥。

商城优惠券类型：满减券、无门槛现金券、折扣券、运费券。

同一次结算可以使用：

- 一张商品优惠券（满减/现金/折扣三选一）；
- 一张运费券。

纯积分和固定组合支付不参与活动价或商城优惠券。

商城券来源：活动领取、定向发放、售后补偿；不允许转赠。

管理员可作废未使用券。批量作废并自动补发只允许超级管理员，替代券必须同类型、实际价值不低于原券、门槛不提高、适用范围不缩小且有效期不短于原剩余期限。

### 14.6 护理兑换权益

积分兑换护理后生成独立护理权益，用户在有效期内再选择技师和时间。预约仍遵守排班、缓冲、最短提前时间、取消改期条款、完成确认、评价和售后规则。

### 14.7 简单库存

支持：手工入库、调整、冻结、释放、发货扣减、退回待检、恢复、报损和库存预警。

不开发采购单、供应商、仓库调拨或复杂成本系统。任何库存调整必须记录原因、调整前后数量、操作人和审计编号。

### 14.8 配送、自提和运费

商品可配置：仅自提、仅配送或两者均可。

运费模板支持：按件、按重量、地区差异、禁配地区、附加费、积分/件数/商品金额包邮。不同模板分别计算，同模板可合并。

一期物流由管理员手工填写物流公司和运单号，不展示虚假轨迹。用户可主动确认收货；发货 15 个自然日后无异常或售后则自动确认。

### 14.9 实物售后

商品独立配置是否支持 7 天无理由、开封限制、运费责任、换货和售后期限。质量问题、错发、漏发、物流损坏、丢失始终可申请。

退货验收流程：

```text
提交售后
→ 审核
→ 用户寄回
→ 退回待检
→ 管理员验货
   ├→ 通过：返还积分/人民币/运费，恢复或报损库存
   └→ 不通过：说明原因并留凭证
```

未验货通过前不得返还积分或运费。

## 15. 老客户与历史卡项导入

管理平台支持 Excel：下载模板、上传、预检、错误报告、确认导入、进度、结果和历史批次。

工作表建议：

- 客户资料；
- 次数组合卡；
- 组合卡护理明细；
- 储值卡；
- 折扣卡。

匹配顺序：

```text
来源系统 + 原会员编号
→ 标准化手机号
→ 无法唯一匹配进入人工处理
```

资料冲突：系统空字段可补充；系统已有不同值不覆盖，进入人工确认。唯一字段冲突时暂停该客户及其卡项导入。

每张历史卡独立导入，保留来源系统、原卡号、原购买日期、到期日和剩余权益，不与新卡合并。唯一性建议为 `source_system + original_card_no`。

余额和次数导入后必须生成 `LEGACY_IMPORT` 流水。重复文件、重复批次和重复记录不得重复发卡。

普通管理员可上传和预检，正式执行导入仅超级管理员可操作。

## 16. 通知中心

一期真实实现站内消息，预留短信和微信通知适配器。

高优先级事件包括：候补空位、服务完成确认、售后处理结果、积分即将到期、订单发货和优惠券替换。

通知必须有投递状态、已读状态、业务对象、模板版本、幂等键和失败原因。未配置外部渠道时只发送站内消息，不伪造短信或微信成功。

## 18. 数据、事务与安全约束

1. 所有关键写接口要求 `Idempotency-Key`；同键同载荷返回原结果，同键异载荷返回冲突。
2. 更新使用 `version` 或 `If-Match`，禁止最后写入覆盖。
3. 金额使用整数分或十进制类型，禁止浮点；积分为整数。
4. 时间使用带时区 ISO-8601，业务自然日按门店时区。
5. 预约时间锁、积分冻结、库存冻结、优惠券锁定和订单创建必须使用事务或可证明的补偿一致性。
6. 资金、积分、卡项、库存、优惠券和通知投递必须使用追加流水或冲正，不能直接覆盖历史事实。
7. 日志不得记录完整手机号、收货地址、健康信息、支付密钥、验证码、访问密码或银行卡敏感信息。
8. 银行卡聚合支付优先使用第三方托管收银台，系统不得存储卡号、CVV、PIN 等敏感认证数据。
9. 密钥在后台录入后加密或写入 Secret 存储；数据库只保存密文或引用，页面只显示掩码。
10. 所有高风险操作保存请求编号、操作账号、设备信息、原值、新值、原因、结果和关联业务对象。

## 19. API 与版本策略

- 保留现有 `/api/v1`、`/api/v2` 兼容边界，但本期新增正式契约优先使用 `/api/v3` 或项目当前最新正式版本。
- 项目组 在 SC1 必须先列出现有接口、表和服务，不得凭空新建重复模型。
- 用户端与管理端接口分离权限，但共享同一领域应用服务。
- 任何 `shop_id`、`user_id`、`technician_id`、订单金额、积分和优惠结果都由服务端重新校验。
- 所有状态机写入返回稳定错误码和 `request_id`。
- API 文档必须同步请求、响应、权限点、幂等、状态前置条件和错误语义。

### 阶段 SC5：积分账户、任务与商城

**范围：** 积分批次/流水/有效期/到期提醒、比例覆盖、上限、签到阶梯、普通订单积分抵扣、商城商品/SKU/库存/购物车/拆单/合包/优惠券/配送自提。

**验收：** 积分、库存和订单并发一致；退款准确恢复原批次；三种购买模式共用库存；购物车拆单和合包可追溯。

### 阶段 SC6：履约确认、评价与售后

**范围：** 24 小时顾客完成确认、评价版本和公开审核、低分自动售后、7 天服务售后、48 小时结案、实物退换货和验货。

**验收：** 重复完成不重复核销；评价删除不清除审计；售后资产操作受阈值限制；未验货不得返还积分或运费。

### 阶段 SC7：历史数据导入与运营管理平台完善

**范围：** Excel 模板、预检、冲突处理、批次幂等、历史卡独立导入、移动高频管理页、基础统计。

**验收：** 重复导入不重复建用户/发卡；冲突资料不覆盖；普通管理员不能正式导入；敏感数据不进入日志。

### 阶段 SC8：双端 DEMO 与客户验收

**范围：** V3.0 Quick Tunnel、演示门禁、固定账号、模拟短信/支付、完整种子数据、一键启动/停止/备份/重置。

**验收：** 电脑和手机完整走通注册、预约、卡项、积分、商城、发货、评价和售后；重置后固定数据恢复；停止后公网立即失效。

### 阶段 SC9：生产部署准备

**范围：** Linux Compose、TLS、Secret 隔离、对象存储、备份恢复、监控告警、真实支付/短信/物流适配器安装机制、Go/No-Go 门禁。

**验收：** 干净 Linux 主机可重复部署；备份可恢复；生产不存在 DEMO 模拟降级；真实渠道必须经 Sandbox、小额支付、退款和对账验收后启用。

### 阶段 SC10：微信小程序

**前置：** SC2-SC9 的 H5/Web 和后端验收通过。

**范围：** 微信身份绑定、小程序页面、上传、分享、支付和订阅消息适配，不重写业务状态机。

**验收：** 同一手机号在 H5 和小程序对应同一会员资产；小程序无法绕过后端规则；核心回归与 H5 结果一致。

## 24. 一期最终验收闭环

一期必须完整演示以下链路：

```text
管理员配置首页、护理项目、技师排班、卡项、积分规则和商城
→ 游客浏览
→ 用户注册/登录
→ 查看技师空闲时间或进入候补
→ 单次项目支付/卡项预约
→ 到店、服务中、顾客完成确认
→ 卡项/订单核销并获得积分
→ 用户评价，低分进入售后
→ 管理员处理退款/权益/补偿
→ 用户确认售后结果
→ 用户签到和使用积分
→ 商城纯现金/纯积分/组合购买
→ 自提或配送、发货、确认收货
→ 退换货验货并准确返还积分/资金/库存
```

任何一条链路出现重复扣款、重复发卡、重复扣积分、负库存、重叠预约、越权读取或无法追溯的资产修改，一期不得通过。
