# M2 基础资料与资源发布/回滚 Runbook

## 发布前门禁

1. 阅读 PRD、数据库设计、API 清单、阶段实施文档和 M2 影响分析。
2. 执行后端 `mvn.cmd clean verify`。
3. 构建 `admin-next` 和 `front-next`。
4. 在隔离 MySQL 8 执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File E:\face\scripts\verify-m1-v3-security.ps1 -VerifyM2Ui
```

5. 确认迁移版本为 `2026072803`，资源并发、幂等、审计、M1 安全回归和
   M2 管理端窄屏/桌面检查全部为 PASS。

## 灰度顺序

1. 先部署兼容后端，不开放 M2 管理入口。
2. 验证 V1/V2 登录、项目、员工、排班和预约读取。
3. 对内部店长开放项目/技能/排班/资源维护。
4. 再开放预约资源选择，观察 409 和 InnoDB 锁等待。
5. 稳定后扩大门店范围。

## 异常处置

| 异常 | 处置 |
|---|---|
| Flyway 失败或 checksum 漂移 | 停止发布；不改 history；从备份重建影子库 |
| 资源冲突出现双成功 | 立即关闭资源选择和 M2 写入口，保留事务日志并回退应用 |
| 锁等待/死锁升高 | 停止扩流，检查排序锁和慢事务，不绕过 `FOR UPDATE` |
| 技能当前版本重复 | 停止技能写入，保留数据证据，检查唯一约束与迁移状态 |
| 幂等重放异常 | 关闭对应写接口，不取消幂等要求 |
| V1/V2 回归异常 | 回退应用，新表保留，不删除历史 |

## 应用回滚

1. 停止 `/api/v3` M2 写流量和预约 `resource_ids` 输入。
2. 等待进行中的事务结束，记录数据库连接和锁状态。
3. 回退到 M1 应用版本。
4. 旧客户端继续使用 `staff_service`、旧项目和排班字段。
5. 保留 `staff_skill_version`、`service_resource` 和
   `resource_booking`，用于审计和后续恢复。
6. 验证旧预约、登录和门店权限链路。

## 数据恢复

只有发生数据损坏且应用回滚不能恢复服务时，才进入 M0 备份恢复流程。
禁止为消除报错直接删除占用、技能版本、审计或幂等记录。测试和故障日志
不得输出真实手机号、证件、健康信息、密码、令牌或支付凭据。
