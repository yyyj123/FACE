# WEB-PERF 公网访问性能优化计划

阶段边界：只优化已完成的响应式用户端与运营管理平台在 DEMO 公网入口下的访问速度；不进入微信小程序、SC10、正式域名切换或真实渠道开通。

## 已测基线

- 录屏中 `/admin/benefits` 约 4 秒后完成数据解锁，后续路由切换仍有明显等待。
- 同一演示数据下，本机网关接口为 5–24 ms，当前 Quick Tunnel 公网接口为 1.2–1.6 s。
- `cloudflared` 当前连接注册到 `lax01`；公网延迟不是 MySQL 查询或 Spring 业务接口造成。
- 管理端首次刷新会串行等待权限上下文、路由分包和页面数据；DEMO 网关又对带哈希的 Vite 静态资源发送 `no-store`。

## 实施

1. 在管理端路由守卫中并行执行账号上下文刷新和当前路由分包预加载，去掉一段公网串行等待。
2. DEMO 网关仅对 `/admin/assets/` 和 `/client/assets/` 的内容哈希资源发送一年 `immutable` 缓存；HTML、API 和演示门禁继续 `no-store`。
3. 增加管理端与 SC8 网关静态契约，防止串行加载和资源缓存配置回退。
4. 重建管理端与网关，在本机和当前 Quick Tunnel 下重测资源响应头、接口耗时和关键管理路由，再运行 WEB-R 双轮验收。

## 验收标准

- 权限上下文与当前路由代码并行加载，权限拒绝逻辑不变。
- 带哈希的双端静态资源返回 `Cache-Control: public, max-age=31536000, immutable`，HTML 和 API 仍为 `no-store`。
- `admin-next` 测试与构建通过，SC8 静态契约通过，WEB-R `-Run 1` 与 `-Run 2` 可重复通过。
- 公网首开减少一段串行等待，已加载的路由资源在后续访问中直接命中浏览器缓存。
