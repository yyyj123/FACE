# M5 提成、结算、售后与审批生命周期契约

## 1. 不变量

1. 已发布规则不可修改；规则变化创建新版本。
2. 已入账提成不可覆盖或删除；调整和退款只追加新流水。
3. 每条提成保存来源事实、规则版本和计算参数快照。
4. 一个提成流水最多进入一个有效结算批次。
5. 已关闭结算批次不可修改或重开。
6. 售后工单不复制退款、支付、套餐、账户或护理状态机。
7. 审批决定不可覆盖；更改必须创建新审批实例。
8. 前端权限隐藏不能替代服务端租户、门店、角色和 SELF 校验。

## 2. 模块边界

```text
servicecare ──ServiceRecordCompleted──┐
payment ─────PaymentSucceeded─────────┼──> commission
refund ──────RefundCompleted──────────┘         │
                                                v
                                          settlement

member/admin ──> aftersale ──应用服务──> refund/package/account
                       │
                       └──> approval ──决定事件──> aftersale

commission / settlement / aftersale / approval ──> notification
```

- 现有模块只发布事实或调用公开应用服务。
- 禁止任何模块直接写其他模块私有表。
- 跨域异步协作使用 outbox，消费者以稳定业务键幂等。

## 3. 提成生成

### 3.1 输入事实

- 服务提成：已完成护理记录、执行技师、项目快照和完成时间。
- 销售提成：已成功支付订单、销售归属员工、订单明细快照和支付时间。
- 退款冲正：成功退款、原支付/订单、退款金额和原提成流水。

### 3.2 规则选择

规则按以下稳定顺序选择：

1. 租户与门店范围匹配。
2. 来源类型和项目/商品/套餐范围匹配。
3. 员工/角色范围匹配。
4. 业务发生时间落在规则生效区间。
5. 优先级从高到低。
6. 同优先级仍出现多条有效规则时拒绝计算并生成异常待办。

规则发布时必须阻止同范围、同优先级和生效区间重叠。

### 3.3 金额计算

- 金额使用 `DECIMAL`，API 使用十进制字符串。
- 计算基数、比例、固定额、封顶、保底和舍入方式写入快照。
- 结果按人民币分舍入；禁止使用浮点。
- 相同输入事实与规则版本必须得到相同结果。

### 3.4 幂等

业务唯一键：

`tenant + source_type + source_id + staff_id + entry_type`

同键同事实返回原提成；同键不同快照返回冲突，不静默覆盖。

## 4. 冻结、结算与退款冲正

### 4.1 冻结

- 提成生成后为 `PENDING`。
- 到达争议期或经授权人工动作后进入 `FROZEN`。
- 冻结保存批次、操作者、时间和原因。
- 冻结不是删除，也不改变原金额。

### 4.2 结算

- 仅 `FROZEN` 且未进入有效批次的提成可纳入结算。
- 结算批次保存周期、门店、币种、总额、版本和责任人。
- 结算明细引用提成流水并保存结算时金额。
- `CONFIRMED` 后明细不可覆盖；取消需整批作废并创建新批次。
- `PAID/CLOSED` 后只允许通过后续批次补差。

### 4.3 退款冲正

| 原提成状态 | 处理 |
|---|---|
| `PENDING` | 追加负向冲正，原流水派生标记为已冲正 |
| `FROZEN` | 追加负向冲正并进入同一待结算核对范围 |
| `SETTLED` | 追加负向冲正，进入下一结算批次 |

冲正唯一键：

`tenant + refund_id + original_commission_entry_id`

原流水金额、规则版本、来源事实和历史结算明细均不得修改。

## 5. 售后工单

- 工单创建保存会员、门店、订单/服务引用、类别、优先级和安全摘要。
- 健康信息、支付凭据和完整敏感正文不进入普通日志/outbox。
- 每次状态变化以 `after_sale_case_log` 追加记录。
- 涉及退款、账户、套餐或库存补偿时调用对应应用服务。
- 售后工单关闭不表示退款必然成功；必须展示真实业务子状态。

## 6. 审批

- 业务模块提交审批请求并保存 `business_type`、`business_id` 和安全摘要。
- 审批步骤保存候选权限/角色、决定人、决定、时间和原因。
- 申请人与最终审批人职责分离。
- 超额度或跨门店必须升级至具备更大数据范围的审批人。
- 决定后通过同事务回调或 outbox 通知业务模块。
- 决定不可覆盖；撤销或复议创建新实例并关联原实例。

## 7. 通知

- 站内通知以接收人和事件去重。
- 业务事务成功后创建或经 outbox 投递通知。
- 通知失败进入可重试状态，不回滚已经成功的资金或审批业务。
- 仅接收人可查询和标记已读。
- 外部通道未配置时记录 `UNAVAILABLE`，不得标记为已送达。

## 8. 故障处理

- 规则歧义：不生成提成，记录异常待办和审计。
- outbox 重复：消费者幂等返回原结果。
- 退款成功但提成冲正待处理：冻结相关提成和结算入口，持续重试并告警。
- 结算并发：版本冲突返回 409，不合并覆盖。
- 审批回调失败：保留已决定实例，通过 outbox 重试业务回调。
- 数据库不可用：readiness 为 DOWN，关键写不得降级为内存成功。
